# Research: Reduce Firestore Read Load from the MCP Connector

**Input**: `spec.md`, and the in-session investigation (2026-08-12) of a live `RESOURCE_EXHAUSTED` incident traced to `/api/mcp` and `/api/mcp/token` traffic, plus direct inspection of the current `retro-rocket/server/src` tree and `retro-rocket/server/vitest.config.ts`.

## §1. Connection-authorization short-lived cache (Story 1, FR-001)

**Current state** (confirmed by direct code read): `mcpAuthMiddleware.ts` performs a live `deps.connectionStore.getConnectionById(claims.connectionId)` read plus an unconditional `deps.connectionStore.saveConnection(connection.touched(now))` write on every single `/api/mcp` call, deliberately — to satisfy the existing requirement (Clarification 2026-07-27 Q1 of feature 015) that a revoked connection is rejected on its very next request.

**Decision**: Wrap the connection lookup in an `InMemoryTtlCache<string, McpConnection>` (feature 040's existing generic, `server/src/adapters/cache/InMemoryTtlCache.ts`), keyed by `connectionId`, TTL = 10 seconds (the upper bound of the 5-10s window from Clarifications — chosen at the upper bound because it maximizes the read reduction while staying within the agreed limit, matching 040's own precedent of picking the clarified value directly rather than an arbitrary point inside the range). On a cache hit, skip both `getConnectionById` and the `touched(now)`/`saveConnection` write entirely for that request (the `lastUsedAt` timestamp update is a nice-to-have, not a correctness requirement — batching it to once per cache window is an accepted, unstated side benefit, not a new requirement). On a cache miss (first call for a connection, or 10s after the last one), perform the live read and write as today, and populate the cache with the fresh result.

**Revocation interaction**: `RevokeConnection.ts` (the use case behind `DELETE /api/mcp/connections/:id`) MUST evict that `connectionId` from the same cache instance at the moment it revokes, so a same-instance revoke-then-call sequence is still rejected immediately — the 5-10s staleness window per Clarifications is the accepted bound only for the case where the cache was already populated before the revoke arrived on a *different* code path than the one holding the cache (there is only one process-wide cache per instance, so this reduces to: revocation issued through this same backend instance is instant; the residual staleness is inherent to any per-instance cache and is exactly the bound Clarifications already accepted).

**Alternatives considered**:
- *No caching, reduce the write only (skip `saveConnection` when `lastUsedAt` is recent)* — rejected: this still leaves the read on every call, which is the larger of the two costs and the one directly implicated in the incident.
- *Cache the boolean "is active" result instead of the full `McpConnection`* — rejected: `mcpAuthMiddleware` also needs `connection.data.uid` for the `claims.sub` cross-check; caching the full object is no more expensive and avoids a second, narrower cache shape for no benefit.

## §2. Failed-authorization backoff (Story 1, FR-002)

**Current state**: No existing mechanism bounds the cost of repeated failed `/api/mcp` authorization attempts. The incident's log evidence showed a burst of `POST /api/mcp` calls returning 401 roughly once every 1-2 seconds, sustained — consistent with a client retrying without backoff after failing to obtain or use a valid Bearer token.

**Decision**: A small in-process fixed-window counter, `InMemoryTtlCache<string, { count: number }>` (or a dedicated tiny structure with the same TTL-reset semantics — implementation detail for `/speckit-tasks`), keyed per Clarifications by the registered MCP `client_id` when the request can resolve one, falling back to the request's origin IP otherwise. On the 5th failed authorization attempt within a 30-second window for a given key (see "Window algorithm" below for the fixed-vs-sliding decision), subsequent attempts from that same key are rejected immediately (without attempting token verification or any Firestore read) for 30 seconds, per Clarifications' agreed threshold.

**Where `client_id` comes from on a failing `/api/mcp` request**: `POST /api/mcp` itself carries no `client_id` in its body (it's Bearer-token-authenticated, not client-credentials-authenticated) — the JWT claims (`McpAccessTokenClaims.clientId`) are only available *after* a successful `tokenService.verify()`, which by definition doesn't happen for a garbage/expired token. This means most of the observed incident traffic (invalid/expired bearer tokens with no verifiable claims) will resolve to the IP fallback, not `client_id` — consistent with Clarifications' explicit acceptance of the IP fallback as the common case, not an edge case. `client_id` is usable as the primary key specifically for the `/api/mcp/token` failure path (`exchangeMcpToken`'s existing `grant_type`/`client_id` body fields, already read by `mcpTokenKeyGenerator` today for a different purpose — rate-limit keying, not backoff) and for any `/api/mcp` request whose Bearer JWT *does* parse and verify but fails the subsequent `connectionStore.getConnectionById` / `uid` cross-check (a revoked-but-structurally-valid token) — in that case `claims.clientId` is available before failing.

**Window algorithm**: fixed-window reset, not a true sliding window — the counter starts at the first failure for a key, counts up for 30s, and resets to 0 exactly 30s after that first failure (regardless of when subsequent failures within the window landed), mirroring `express-rate-limit`'s own default fixed-window algorithm already governing `tokenLimiter`/`toolLimiter` in this same file (Principle V, Simplicity — a true sliding window needs a timestamp-per-attempt log instead of a single counter, for a difference that doesn't matter at this threshold/window size).

**IP-keyed backoff never blocks a token that verifies successfully** (found during implementation): the IP-keyed check is applied only to requests with a missing token or one that fails `tokenService.verify()` — never to a request whose token verifies, even if that same IP has recent unrelated failures. Checking IP backoff unconditionally (before verification) would collaterally block a different, genuinely valid client sharing the same network origin as a misbehaving one, for the remainder of the 30s window — worse than the problem being solved. A verified-but-otherwise-rejected token (revoked/mismatched connection) is instead bounded by its own `client_id`-keyed backoff (already the design above), which only affects that specific client's own repeated failures.

**Alternatives considered**:
- *Key by IP only, always* — rejected: Clarifications explicitly asked for `client_id`-when-resolvable specifically to avoid collapsing distinct legitimate MCP client deployments (or users behind the same NAT/proxy) into one shared IP bucket, mirroring the reasoning already documented in `mcpTokenKeyGenerator`'s own comment for `tokenLimiter`.
- *Permanent block after threshold (require manual reset)* — rejected: not requested by Clarifications (which specified a 30s backoff, not a permanent one) and would risk permanently locking out a legitimate client that happened to misconfigure itself briefly.
- *True sliding window (timestamp log, evict entries older than 30s on each check)* — rejected as the default: more precise (no reset-boundary edge case where a burst spanning a window boundary evades the threshold), but adds bookkeeping this codebase's existing rate-limit precedent (`express-rate-limit`'s own default) doesn't use either; revisit only if the fixed-window boundary edge case proves to matter in practice.

## §3. Per-identity MCP tool-call rate limiting (Story 1, FR-003)

**Current state**: `toolLimiter` in `mcp.ts` is deliberately IP-keyed today (`rateLimit({ ... })` with the default IP key generator), per an explicit in-code comment deferring the per-identity change "until a spec calls for it" — this spec now calls for it.

**Decision**: Change `toolLimiter`'s `keyGenerator` to return the authenticated uid (`res.locals.mcpAuth.sub`, populated by `mcpAuthMiddleware` which runs immediately before `toolLimiter` in the route's middleware chain — see `router.post('/api/mcp', toolLimiter, mcpAuthMiddleware(deps), ...)` today, which needs its **order swapped** so auth resolves the identity before the limiter needs it: `mcpAuthMiddleware(deps), toolLimiter`). The existing numeric threshold (120 requests/minute) is unchanged — Clarifications resolved the *keying* ambiguity, not the numeric value, and re-keying an already-reasonable existing number to per-identity is a strict improvement with no indication a different number is needed.

**Middleware order change is in scope, not incidental**: `toolLimiter` currently runs *before* `mcpAuthMiddleware` specifically because IP is available pre-auth. Re-keying by uid makes the limiter dependent on auth having already resolved, so the two middlewares must be reordered on this one route. This also means an unauthenticated (401) request no longer consumes a `toolLimiter` slot at all — it is naturally covered by the FR-002 backoff instead, which is the more appropriate bound for auth-failure traffic (§2).

**Alternatives considered**:
- *Keep IP-keyed but raise the threshold* — rejected: does not address the root ambiguity (shared infrastructure collapsing distinct users), only masks it with a bigger shared bucket.

## §4. Deduplicate `listCards` inside `listSentimentResults` (Story 2, FR-004)

**Current state**: `FirestoreRetrospectiveReadAdapter.listSentimentResults(retrospectiveId)` calls `this.listCards(retrospectiveId)` internally to derive `cardIds`, even though both `GetRetrospectiveDetail` and `GetRetrospectiveSummary` already call `listCards(retrospectiveId)` directly in their own `Promise.all`, alongside the `listSentimentResults` call — the `cards` collection is queried twice per detail/summary call.

**Decision**: Change `RetrospectiveReadPort.listSentimentResults`'s signature from `(retrospectiveId: string)` to `(cardIds: string[])` (`data-model.md`). `GetRetrospectiveDetail.ts` and `GetRetrospectiveSummary.ts` derive `cardIds` from the `cards` result already present in their own `Promise.all` and pass it through; `FirestoreRetrospectiveReadAdapter.listSentimentResults` no longer needs — or has — a `retrospectiveId` parameter at all, only the chunked `'in'` query over the given ids (unchanged).

**Alternatives considered**:
- *Add a per-request cache inside the adapter instead of changing the port signature* — rejected: introduces request-scoped state into a class that today holds no state at all (deliberately, since a single adapter instance is process-lifetime, not request-scoped — see §1's connection cache and `FirestoreProfileAdapter`'s existing 60s cache, both keyed and TTL'd precisely because the adapter is *not* request-scoped); a pure signature change is simpler (Principle V) and requires no new state or invalidation reasoning at all.
- *Have `listCards` itself cache its own last result and have `listSentimentResults` opportunistically reuse it* — rejected: implicit, order-dependent coupling between two independently-callable port methods is a worse interface than making the existing data dependency explicit in the signature.

## §5. Batch `listRetrospectivesForUser`'s per-id lookups (Story 2, FR-005)

**Current state**: For each retrospective id the user participates in (but doesn't own), `listRetrospectivesForUser` issues one `this.db.collection(RETROSPECTIVES).doc(id).get()` inside a `for` loop — N individual point-reads for N joined-but-not-owned retrospectives.

**Decision**: Replace the loop with a single batched read using the Admin SDK's `db.getAll(...refs)` (a native multi-document-get RPC, one round trip regardless of count — distinct from a Firestore query, so it needs no `'in'`-clause 30-item cap; unlike a query, `getAll` has no server-side item-count ceiling worth chunking for at this table's realistic scale, but the existing chunk-at-30 pattern from `listSentimentResults` is reused anyway for consistency and to bound the size of any single RPC payload, matching this codebase's already-established convention rather than introducing an unbounded-payload single call as a new pattern).

**Alternatives considered**:
- *A `'in'` query on document ID (`where(FieldPath.documentId(), 'in', chunk)`)* — rejected in favor of `getAll`: `getAll` is the more direct Admin SDK primitive for "fetch these exact document references" (no query planning, no field-path indirection) and is already how this codebase's multi-doc-by-id reads are idiomatically expressed elsewhere in `firebase-admin` usage patterns; either would satisfy `FR-005`, but `getAll` needs no `FieldPath` import or query-clause construction for what is fundamentally a batch point-read.

## §6. Short-lived cache for `get_retrospective_detail`/`get_retrospective_summary` (Story 3, FR-008)

**Current state**: Both tools always assemble their response from live `Promise.all([listCards, listGroups, listSentimentResults, listActionItems])` (plus `getRetrospective`/`listParticipants` for the access check, and `listFacilitatorNotes` conditionally) — no caching, by original design.

**Decision**: Wrap the *assembled result* (not the individual sub-queries) in an `InMemoryTtlCache<string, RetrospectiveDetailOutput>` / `<string, RetrospectiveSummaryOutput>` — two separate cache instances (detail and summary have different shapes and partially different access-gating for `facilitatorNotes`), each keyed by `retrospectiveId`, TTL = 15 seconds (the upper bound of the 5-15s window from Clarifications, for the same "maximize reduction within the agreed bound" reasoning as §1). Caching happens **after** the access-control check (`hasRetrospectiveAccess`), not before — the cache stores the fully-authorized, per-tool-call result shape, so a cache hit still requires the caller to have independently passed today's live access check for *that specific call*, preserving `FR-006` (no access-control change). Concretely: the access check and the two participant/retrospective reads it depends on stay live and un-cached (they are already cheap — a single doc read plus a single query, not the 4-6 queries the cache is meant to save); only the expensive `Promise.all` fan-out is memoized.

**Why per-tool-call access checks stay live while the fan-out is cached**: caching a per-user-scoped result and serving it to a *different* user who separately has access would be safe read-wise (both are legitimately authorized) but would require the cache key to include the requester's uid whenever `facilitatorNotes` visibility differs by requester (`canIncludeFacilitatorNotes`) — simpler to keep the access decision and the notes-inclusion decision live per call (cheap) and only cache the requester-independent expensive part (cards/groups/sentiment/actionItems), then re-attach `facilitatorNotes` live after the cache read if the *current* caller qualifies. This avoids ever needing uid in the cache key.

**Alternatives considered**:
- *Cache the fully-assembled per-requester output including `facilitatorNotes`* — rejected: would require keying by `(retrospectiveId, requesterUid)`, fragmenting the cache far below its potential hit rate (most callers are the retrospective's own participants hitting the same board, not one uid repeatedly) for a field that's small and cheap to re-check live.
- *A longer TTL for more savings* — rejected: 15s is Clarifications' explicit upper bound; going beyond it is out of this feature's scope without a new clarification.

## §7. Testing strategy for `FirestoreRetrospectiveReadAdapter.ts` changes

**Confirmed convention** (per `FirestoreProfileAdapter.ts`'s own docstring, which explicitly names `FirestoreRetrospectiveReadAdapter` alongside itself): this codebase's Firestore adapters have no dedicated Vitest-level test for their live query composition — only pure, exported helper functions (if any) are unit-tested directly, and the adapter's actual Firestore behavior is verified end-to-end by Playwright against the emulator. §4, §5, and §6 above introduce no new pure/exported helper functions worth extracting on their own (the `getAll` batching and the two `InMemoryTtlCache` wrappings are thin composition, not standalone logic), so all three are verified via `e2e/mcp-connector.spec.ts` extension, not a new adapter-level Vitest file — consistent with, not a deviation from, established practice.

**What stays Vitest-testable**: §4's port-signature change (`listSentimentResults(cardIds)`) is exercised at the **use-case** layer (`GetRetrospectiveDetail.test.ts`/`GetRetrospectiveSummary.test.ts`), which already uses fake `RetrospectiveReadPort` implementations — asserting the fake's `listSentimentResults` receives the cardIds derived from the already-fetched `cards`, not a fresh independent lookup, is a pure call-graph assertion needing no Firestore double. §1 and §2 (`mcpAuthMiddleware.ts`) and §3 (`toolLimiter` keying/ordering in `mcp.ts`) are HTTP-layer code depending only on ports (`McpConnectionStorePort`, `McpTokenServicePort`) already faked in `server/test/application/use-cases/mcp/mcpFakes.ts`, so they get full Vitest coverage as today.
