# Feature Specification: Reduce Firestore Read Load from the MCP Connector

**Feature Branch**: `041-reduce-mcp-firestore-reads`

**Created**: 2026-08-12

**Status**: Draft

**Input**: User description: "Formaliza en una nueva feature la investigación anterior sobre la propuesta de mitigación para firebase sobre mcp" — formalizing the in-session investigation (2026-08-12) into a Firestore `RESOURCE_EXHAUSTED` incident traced to traffic on the MCP connector (`/api/mcp`, `/api/mcp/token`), and the mitigation proposal that followed it. This is a sibling incident to the one addressed by feature 040 (board join/reconnect and real-time listener traffic) — same anti-abuse throttle, different traffic source, confirmed still occurring after 040 shipped.

## Clarifications

### Session 2026-08-12

- Q: Should the read-only `get_retrospective_detail` / `get_retrospective_summary` MCP tools be allowed to serve results from a short-lived cache (introducing a small staleness window), or must every call remain a fully live read of the underlying data, as it does today? → A: Yes — a short cache window (5-15 seconds) is acceptable. Story 3 is in scope for this feature.
- Q: For the connection's revoked/active status check performed on every MCP tool call, what is the maximum acceptable delay between a connection being revoked and that revocation being enforced on the next call? → A: A short bounded window (5-10 seconds) is acceptable if it substantially reduces read volume — the revocation does not need to be effectively immediate, but must be bounded and short.
- Q: FR-002 requires bounding the backend work generated by repeated, rapid, failed MCP authorization attempts — but an invalid/expired credential typically does not resolve to a real user identity (as observed in the incident: a burst of 401s with no resolvable uid). What should that bound be keyed on? → A: The registered MCP client identifier (`client_id`) when it is present in the request, falling back to the request's origin IP when it is not.
- Q: What concrete threshold should trigger the failed-authorization backoff, and for how long? → A: 5 failed attempts within 30 seconds triggers a 30-second backoff, from the same key established above.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - MCP access keeps working during traffic bursts (Priority: P1)

An AI assistant connected to RetroRocket through the MCP connector is being used normally — listing retrospectives, pulling a summary, checking a detail — possibly with several tool calls in quick succession (a single conversation turn that needs more than one piece of data, or a client retrying after a transient hiccup). This must not push the backend's data store past its anti-abuse threshold and start failing requests platform-wide, the way it did during the incident investigated on 2026-08-12 (a burst of MCP tool calls and repeated failed authorization attempts coincided with `RESOURCE_EXHAUSTED` errors on unrelated endpoints like profile lookup).

**Why this priority**: This is the confirmed, currently-occurring cause of a production incident — the same class of failure feature 040 fixed for board traffic, now identified on the MCP connector instead. Highest-impact, most user-visible risk (a failure here degrades the platform for everyone, not just MCP users), and already has evidence and a concrete diagnosis behind it.

**Independent Test**: Can be tested by issuing a rapid sequence of authenticated MCP tool calls (and a sequence of calls with invalid/expired credentials) against an already-connected client and confirming the data-store read volume per call, and the platform's behavior under repeated auth failures, both stay within a safe margin of the anti-abuse threshold.

**Acceptance Scenarios**:

1. **Given** an MCP client with a valid, active connection, **When** it makes several tool calls in quick succession, **Then** the connection's authorization is confirmed without issuing a fresh data-store read on every single call.
2. **Given** an MCP client presenting an invalid, expired, or unrecognized credential, **When** it repeats failed attempts rapidly without pausing, **Then** the system limits how much backend work those repeated failures can generate, rather than treating each attempt as a full-cost request indefinitely.
3. **Given** multiple distinct users connected through the same MCP client software (which may share network infrastructure), **When** they each make tool calls, **Then** one user's call volume does not consume another user's allowance or vice versa.

---

### User Story 2 - No duplicate data-store lookups within a single MCP tool call (Priority: P2)

When an AI assistant asks for a retrospective's detail or summary, the system gathers several related pieces of that retrospective's data (cards, groups, sentiment, action items, etc.) to build the response. Some of that gathering currently repeats itself — the same underlying data is fetched more than once while producing a single answer.

**Why this priority**: A steady, avoidable cost on every detail/summary call, independent of traffic spikes — reducing it lowers the baseline load and increases the safety margin before the next burst trips the same anti-abuse protection. Lower priority than Story 1 because it didn't by itself trigger the incident, but it compounds with it.

**Independent Test**: Can be tested by requesting a retrospective's detail or summary and confirming the underlying data needed to build that single response is fetched once per distinct piece of data, not more.

**Acceptance Scenarios**:

1. **Given** a retrospective with cards, **When** its detail or summary is requested, **Then** the card data behind that response is fetched exactly once, not once directly and again indirectly while computing a derived part of the same response.
2. **Given** a user who participates in (but does not facilitate) several retrospectives, **When** they ask to list the retrospectives they have access to, **Then** the number of individual per-retrospective lookups needed to build that list does not grow one-at-a-time per retrospective as their count increases.

---

### User Story 3 - Result caching for read-only retrospective lookups (Priority: P3)

Beyond removing outright duplication (Story 2), the detail/summary lookups themselves are served from a short-lived cache (5-15 seconds, per Clarifications) instead of always re-reading live, further cutting read volume for repeated or near-simultaneous requests for the same retrospective.

**Why this priority**: Highest potential additional impact, but it changes an existing, deliberate behavior (every MCP read is live, with no caching) rather than only removing redundant work — sequenced after the lower-risk, no-behavior-change wins in Stories 1 and 2 so those ship first.

**Independent Test**: Can be tested by making two requests for the same retrospective's detail or summary within the 5-15 second cache window and confirming the second is served without a full fresh reload of every underlying piece of data, and that a request issued after the window has elapsed reflects any intervening change.

**Acceptance Scenarios**:

1. **Given** the same retrospective's detail or summary requested twice within the 5-15 second cache window, **When** the second request arrives, **Then** it is answered without repeating the full set of underlying reads the first request performed.
2. **Given** a retrospective whose data changes after being cached, **When** the cache window (5-15 seconds) elapses, **Then** a subsequent request reflects the change.

---

### Edge Cases

- What happens when many distinct MCP clients (not just one misbehaving one) each make a burst of legitimate calls at the same time — does the mitigation for Story 1 distinguish "one client retrying too fast" from "many clients, each within their own reasonable limits"?
- How does the system behave if a connection is revoked at the exact moment a cached or recently-confirmed authorization check would otherwise have let a call through (see Clarifications)?
- What happens when a retrospective referenced by a cached (Story 3) detail/summary result is deleted before the cache entry expires? Implicitly covered by FR-008's accepted staleness window — a deleted retrospective's cached result may still be served for up to 15 seconds after the deletion, the same bound FR-008 already accepts for any other data change.
- How does the repeated-failure mitigation in Story 1 avoid also penalizing a legitimate client that happens to have one connection expire and correctly reconnects once (as opposed to retrying the same failing credential indefinitely)?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST avoid issuing a fresh data-store read of a connection's authorization/revocation status on every single MCP tool call when the same connection has been recently confirmed active, reusing that confirmation for no more than 5-10 seconds (per Clarifications) before it must be re-checked.
- **FR-002**: The system MUST temporarily back off further authorization attempts, for 30 seconds, from a client that has accumulated 5 failed MCP authorization attempts within a 30-second window (per Clarifications), keyed by the registered MCP client identifier (`client_id`) when present in the request, falling back to the request's origin IP when it is not — so that a client stuck retrying cannot indefinitely consume data-store capacity.
- **FR-003**: The system MUST track and limit MCP tool-call volume per authenticated identity rather than per shared network origin, so that distinct users are not collapsed into (or protected by) the same allowance.
- **FR-004**: The system MUST NOT fetch the same underlying collection of retrospective data more than once while assembling a single `get_retrospective_detail` or `get_retrospective_summary` response.
- **FR-005**: The system MUST avoid one-at-a-time, per-item lookups that scale linearly with a user's retrospective count when listing the retrospectives that user has access to; the lookup cost MUST scale sub-linearly (e.g., batched) instead.
- **FR-006**: The system MUST continue to expose only read-only retrospective data through the MCP connector, with no change to who can access which retrospective's data (facilitator/participant access rules unchanged).
- **FR-007**: The system MUST NOT change the shape or content of MCP tool responses as an observable side effect of these efficiency changes.
- **FR-008**: The system MUST serve `get_retrospective_detail` / `get_retrospective_summary` responses reflecting the underlying data as of no earlier than 5-15 seconds before the request (per Clarifications).

### Key Entities *(include if feature involves data)*

- **MCP Connection Authorization State**: Whether a given MCP connection is currently active or has been revoked; checked on every tool call today, a candidate for short-lived reuse per FR-001.
- **MCP Tool Call Identity**: The authenticated user behind an MCP tool call, used to bound call volume per FR-003 instead of per network origin.
- **Retrospective Detail/Summary Result**: The assembled, read-only projection of one retrospective's data (cards, groups, sentiment, action items, participants, and — where visible — facilitator notes) returned by the `get_retrospective_detail` and `get_retrospective_summary` tools; a candidate for short-lived caching per Story 3.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A burst of MCP tool-call traffic matching the 2026-08-12 incident's observed magnitude (sustained `POST /api/mcp` traffic at roughly one request every 1-2 seconds, with bursts of 8-10 requests within a 10-second window) no longer results in data-store anti-abuse errors on the MCP connector or on unrelated parts of the platform.
- **SC-002**: The number of distinct data-store reads needed to authorize a sequence of MCP tool calls on the same already-active connection drops to at most one read per 5-10 second window, down from today's one read per call.
- **SC-003**: A client repeating failed authorization attempts without pausing is backed off after its 5th failed attempt within 30 seconds, capping its backend work during that burst instead of generating unbounded volume proportional to its retry rate.
- **SC-004**: Requesting a retrospective's detail or summary performs no more than the minimum number of distinct underlying data lookups needed to answer it — no lookup is repeated within a single request.
- **SC-005**: Listing the retrospectives a user has access to no longer requires one individual lookup per retrospective they participate in; cost grows sub-linearly with their retrospective count.
- **SC-006**: No regression is introduced in MCP tool behavior, response content, or access-control correctness, as verified by the project's existing automated test suite plus targeted new coverage for the changed paths.

## Assumptions

- This feature is scoped to the MCP connector's own request paths (`/api/mcp`, `/api/mcp/token`, and the tool calls served through them) — it does not revisit the board join/reconnect/real-time-listener work already covered by feature 040, whose mitigations remain in place and are assumed functioning.
- The project remains on Firebase's free (Spark) plan for the scope of this feature; solutions that depend on enabling billing are out of scope.
- The three user stories are independently shippable in priority order (P1, then P2, then P3), consistent with feature 040's precedent of not bundling the highest-risk, most-behavior-changing story with the lower-risk quick wins.
- "No user-perceptible change in behavior" is the guiding constraint for Stories 1 and 2, which are pure efficiency changes. Story 3 deliberately introduces a bounded staleness window (5-15 seconds) for detail/summary results, and the connection-authorization check (FR-001) deliberately introduces a bounded staleness window (5-10 seconds) for revocation enforcement — both accepted trade-offs per Clarifications, not accidental regressions.
- Per-identity rate limiting (FR-003) reuses the same notion of "authenticated identity" already established for MCP token-exchange rate limiting elsewhere in the connector, rather than introducing a new identity concept.
