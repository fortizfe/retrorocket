# Phase 0 Research: Fix MCP Connections Always Resolving as Rejected

No items in Technical Context were left as `NEEDS CLARIFICATION` — the spec's `/speckit-clarify` session already resolved the two scope-impacting decisions (preserve-but-rescope the protective mechanism vs. remove it; add rejection-rate alerting vs. tests-only). What follows is the code-level investigation that turns those decisions into a concrete plan.

## 1. Root cause of "connections always resolve as rejected" (FR-001, User Stories 1 & 2)

**Decision**: `tokenLimiter` (`server/src/http/routes/mcp.ts:125-134`), the rate limiter in front of `POST /api/mcp/token`, is keyed by `req.ip` (the `express-rate-limit` default). Its own comment (`mcp.ts:115-124`) explains why: this route is authenticated by the AI client itself (OAuth code/PKCE, or a refresh token), never by the browser's `rr_session` cookie, so — unlike `auth`/`boards`/`profile`/`retrospectives` (`rateLimiting.ts`'s `sessionAwareKeyGenerator`) — there was judged to be "no session identity to key on here."

That reasoning is the defect. `POST /api/mcp/token` is a server-to-server call made by the AI client's own backend (e.g. Claude's hosted remote-MCP-connector infrastructure), not by an individual person's browser. `req.ip`, even correctly resolved through Vercel's proxy hop (`app.set('trust proxy', 1)`, `app.ts:42`), reflects the *calling AI client's* address — which can, and evidently does, represent many different RetroRocket users at once when they all connect through the same hosted AI client. Once the shared 60-requests/15-minutes bucket for that address is exhausted — by any combination of other users' token exchanges, the AI client's own connection retries, or routine access-token refreshes — every subsequent legitimate token exchange sharing that bucket gets a blunt `429 { error: { code: 'rate_limited' } }`, which the AI client has no way to present as anything other than "unable to connect." Because the bucket, once saturated, stays saturated for the rest of its 15-minute window (and a busy shared IP can re-saturate it every window), this reads as a persistent, deterministic "always rejected" condition rather than an intermittent failure — matching the bug report exactly, including that a refresh ("intento refrescar mi conexión") is exactly a `grant_type=refresh_token` call through the same limiter.

**Evidence, not just hypothesis**: `server/test/http/routes/mcpToken.test.ts`'s existing `tokenLimiter` describe block (`mcpToken.test.ts:135-164`) proves the isolation-by-IP mechanism works exactly as designed — two different `X-Forwarded-For` values get independent buckets, the same one gets throttled after 61 calls. It only ever exercises *synthetic, deliberately-distinct* IPs, though; it never represents the actual production condition, two *different users'* requests arriving with the *same* IP because the calling client is shared infrastructure. The mechanism the test documents as correct is precisely the mechanism that fails once that premise (one IP ≈ one user) doesn't hold.

**Why this was not found by 023/024**: `024-fix-mcp-connection-status`'s research.md §6 investigated FR-004 ("no es posible realizar la conexión") and found no OAuth/PKCE semantic defect in `exchangeMcpToken`, concluding the concrete, fixable issue at the time was an observability gap (`InvalidGrantError`'s indistinguishable messages). That investigation never examined `tokenLimiter`, which sits as Express middleware *in front of* the `/api/mcp/token` route handler — a `429` from it never reaches `exchangeMcpToken` at all, so none of 024's improved messages or `'failed'`-status bookkeeping are ever triggered by this failure mode. This is why the underlying "always rejected" symptom persisted after 024 shipped: 024 fixed real, separate problems (a display bug, and an ambiguous revoked-vs-expired error message) but never touched the actual blocking mechanism for this report.

**Alternatives considered**:
- *A logic defect in `exchangeMcpToken`/`AuthorizeMcpConnection`/`RegisterMcpClient`* — re-examined directly for this feature (redirect_uri/client_id matching, PKCE `S256` verification, one-time-use code consumption, refresh-token hash lookup, revoked-vs-active branching) and found spec-conformant, consistent with 024's research.md §6 finding; no change needed there.
- *Missing deployment configuration (`SESSION_SIGNING_KEY`/`MCP_PUBLIC_BASE_URL` unset, `buildMcpDeps` returning `null`)* — would 503 the entire `/api/mcp/*` router unconditionally, an all-or-nothing outage inconsistent with a user reporting a specific "rejected" outcome from a flow that otherwise runs (redirects, consent screen, etc. all work); ruled out.

## 2. Fix design: resolve real per-user identity instead of trusting IP (Clarification Q1 — "preserve, rescope per-user")

**Decision**: Give `tokenLimiter` an async `keyGenerator` (the same capability `rateLimiting.ts`'s `sessionAwareKeyGenerator` already uses for other routers) that resolves the actual `uid` behind the request, using data the request already supplies and store methods that already exist and are non-mutating:

- `grant_type=authorization_code`: read `body.code`, call the existing `connectionStore.getAuthorizationRequest(code)` (a plain read — does **not** consume the code; `exchangeMcpToken` performs the real, consuming read moments later), and key on `record.uid` if found.
- `grant_type=refresh_token`: hash `body.refresh_token` the same way `ExchangeMcpToken.ts`'s private `hashRefreshToken` already does, call the existing `connectionStore.getConnectionByRefreshTokenHash(hash)`, and key on `connection.data.uid` if found.
- If neither resolves (unknown/garbage/malformed input — never a legitimate in-flight attempt), fall back to the current IP-keyed behavior unchanged.

**Rationale**: This directly satisfies Clarification Q1 — the protection is *preserved*, not removed, but its bucket boundary becomes "one user's own activity" instead of "whatever IP happened to originate the request." Two different users can never collide, regardless of what the calling AI client's infrastructure looks like from the outside; a single user's own excessive activity (many rapid retries) still gets throttled, which is the legitimate case Clarification Q1 explicitly wants kept (spec FR-005, SC-004). The unresolvable-identity fallback keeps today's IP-based defense for genuinely invalid/garbage requests, so nothing about abuse protection regresses for that case.

**Alternatives considered**:
- *Widen the shared IP-keyed threshold instead of rescoping* (the rejected Clarification option) — does not fix the underlying problem, only delays it; a large-enough burst across many users would still collide, and there is no principled number to pick since the real cause is bucket-sharing, not an under-sized limit.
- *Key by `client_id` alone* (registered per AI client via DCR, `RegisterMcpClient.ts`) — rejected: `client_id` identifies the *AI client software* (e.g. "Claude"), not the individual RetroRocket user; every user of the same AI client would still collide with each other, reproducing the exact bug.
- *Move `tokenLimiter` to `rateLimiting.ts`'s existing `sessionAwareKeyGenerator`* — rejected: that resolver keys on the `rr_session` cookie, which this route's caller (the AI client's backend) never sends; it would fall straight through to the same broken IP fallback for every request.
- *Remove `tokenLimiter` entirely* — rejected per Clarification Q1; would leave the token endpoint with no abuse/cost protection at all.

`toolLimiter` (`POST /api/mcp`, tool calls made *after* a connection already exists, gated by `mcpAuthMiddleware`) is deliberately left unchanged. It is not part of the connection/token flow this spec's FR-001–FR-007 describe (spec Assumptions: "Legitimate rejection paths... are out of scope," and the spec's Key Entities are scoped to "Connection Attempt"), and per Constitution V (Simplicity/YAGNI) is not touched until a spec calls for it.

## 3. Observability: detecting a future recurrence (Clarification Q2 — "add rejection-rate alerting")

**Decision**: Emit one `metrics.increment('mcp.token.rate_limited', { keyType })` call (`keyType` is `'uid'` or `'ip'`) from `tokenLimiter`'s existing `handler` (`mcp.ts:131-133`), using the project's existing `MetricsPort` (`server/src/application/ports/observability/index.ts`) and its only current implementation, `StdoutMetrics` (`server/src/adapters/observability/stdout.ts`), which already emits structured JSON metric lines to stdout — the same sink Vercel's platform-level log capture already ingests for every other request. `McpRouterDeps` gains a `metrics: MetricsPort` field; `buildMcpDeps` (`mcp-wiring.ts`) gains a `metrics` parameter; `composition-root.ts` passes `observability.metrics` through, the same `Observability` bundle already built there and passed to every other wiring function's logger parameter today.

**Rationale**: `MetricsPort.increment` already exists in this codebase specifically for this purpose (`observability/index.ts`'s doc comment: "Driven adapters implement these so use cases and HTTP wiring depend on interfaces, not a concrete logging/metrics/tracing library") but has zero real callers today (`grep` confirms only `SimpleTracer`'s internal `timing()` use). Adding the first real `increment()` call is using existing infrastructure as designed, not building anything new (Constitution III/V). Tagging by `keyType` makes the signal actionable: a spike in `keyType: 'uid'` events is expected/benign (real users hitting their own limit under heavy retry behavior); a spike in `keyType: 'ip'` events is the exact class of problem this feature fixes and is worth alerting on, since after this fix it should only ever reflect genuinely unresolvable/garbage requests, not legitimate multi-user collisions. External alerting (a Vercel log drain, or whatever log-based monitoring the team already has) is configured against this metric line outside this repository — this feature's job is only to emit the signal, per Constitution V (no new in-app alerting UI/dashboard is warranted for one metric).

**Alternatives considered**:
- *A dedicated new alerting service/dashboard* — rejected: no such infrastructure exists in this codebase, and building one for a single metric is disproportionate (Constitution V, YAGNI).
- *`logger.warn` only, no metric* — rejected: a metric is queryable/alertable as a rate over time; a log line alone requires the same downstream tooling to parse it into a rate anyway, and `MetricsPort` already exists to avoid exactly that. (A `logger.warn` call may still accompany the metric for correlation-id-level debugging, consistent with `errorHandler.ts`'s existing pattern — an implementation detail for tasks.md, not a design decision.)

## 4. Regression surface (FR-006)

**Decision**: No change to `McpConnection` domain logic, `ListConnections.ts`'s active-only filtering (024), `RevokeConnection.ts`, or `ExchangeMcpToken.ts`'s branch logic/messages (024). The fix is isolated to how `tokenLimiter`'s bucket key is computed and one new metric emission on its existing rejection path; the 400/`invalid_grant` semantics 024 shipped are unaffected, and 023's revoked-exclusion behavior is unaffected since it lives entirely in `ListConnections.ts`.

**Rationale**: Confirms the "no domain change" claim in plan.md's Project Structure — this is an HTTP/infrastructure-layer fix only, consistent with Constitution V.
