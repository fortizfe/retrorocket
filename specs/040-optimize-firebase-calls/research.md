# Research: Optimize Backend-to-Firestore Call Volume

**Input**: `spec.md`, and the source investigation `fortizfe/documents/mejora llamadas firebase.md` (Spanish, read-only investigation, no code changes applied). All volumes, thresholds, and current-code citations below trace back to that document plus direct inspection of the current `server/src` tree.

## §1. Deduplicating reads in the `/join` reconnection cycle (Story 1)

**Current state** (confirmed by direct code read):
- `server/src/http/routes/retrospectives.ts`'s `POST /api/retrospectives/:id/join` handler calls `resolveDisplayName()` (→ `ensureUserProfile` → 1 Firestore read of `users/{uid}`) then `joinRetrospective()`.
- `server/src/application/use-cases/retrospective/JoinRetrospective.ts` calls `retrospectiveBoardPort.getRetrospective(id)` — 1 read of `retrospectives/{id}`.
- `server/src/adapters/firebase/FirestoreRetrospectiveBoardAdapter.ts`'s `join()` re-reads the same `retrospectives/{id}` document (`boardRef.get()`) before its transaction, then the transaction itself reads the participant-existence query — 2 more reads.
- Separately, `server/src/http/ws/realtimeUpgrade.ts`'s WS handshake also calls `retrospectiveBoardPort.getRetrospective(id)` for its own existence check.
- `retro-rocket/src/features/boards/retrospective/hooks/useRetrospectiveRealtimeSync.ts` (frontend) calls `joinBoard()` + `getBoardState()` on every WS `onConnect`, not just first mount — confirmed by the source investigation and consistent with the existing code comment in `retrospectives.ts` about this being "the router de mayor volumen."

**Decision**: Two independent, additive changes, both confined to the request/reconnection cycle (no cross-request or cross-instance state):
1. `FirestoreRetrospectiveBoardAdapter.join()` MUST accept an already-fetched `RetrospectiveDTO` (or re-check existence via the same transaction it already opens for the participant query, folding the standalone `boardRef.get()` into that transaction) instead of issuing its own separate `boardRef.get()`. `JoinRetrospective.ts` already has the board from its own `getRetrospective()` call one line above — pass it through.
2. `resolveDisplayName()` MUST reuse a single `ensureUserProfile` result within a request if it is invoked more than once while producing one response — in the `/join` handler today it's only called once, so this specific duplication doesn't currently occur in `/join` itself, but the *same* per-request-reuse principle applies to any single request path where `resolveDisplayName` could be called twice (defensive, not currently exercised).

**Alternatives considered**:
- *Merging the WS-handshake read and the `/join` read into one call* — rejected: they happen over two different transport layers (HTTP `POST /join` vs. the WS `upgrade` event) that are not guaranteed to be sequenced or co-located in the same process invocation from the client's perspective; coalescing them would require session-scoped caching across requests, which is exactly what §2 already covers via the profile cache pattern applied narrowly. Given `getRetrospective` is a single cheap point-read (not the compounding N+1 problem elsewhere), the marginal remaining duplication (handshake vs. join) is accepted as out of scope — the 4-reads-to-1 reduction target in `SC-001` is about the `/join` call's *own* internal duplication, which this fix fully addresses.

## §2. Profile-lookup caching (Story 1 / Story 2 support)

**Current state**: `FirestoreProfileAdapter.ensureProfile()` (`server/src/adapters/firebase/FirestoreProfileAdapter.ts`) does an unconditional `docRef.get()` on every call, with no caching layer anywhere in the call chain.

**Decision**: A per-instance, in-memory TTL cache (`Map<uid, { profile: ProfileRecord; expiresAt: number }>`), TTL = 60 seconds (per clarification), sitting in front of `FirestoreProfileAdapter.ensureProfile()` — either as a decorator implementing `ProfilePort` or as an internal cache inside the adapter itself. Explicit profile writes (`PATCH` display-name updates, `renameParticipantsForUser`) already go through a distinct, deliberate invalidation path per the existing code (`FirestoreRetrospectiveBoardAdapter.renameParticipantsForUser`); the cache entry for the affected `uid` MUST be invalidated (removed, not just left to expire) at that same write site so a rename is never masked by a stale cache hit for up to 60s.

**Rationale for per-instance (not Redis)**: Unlike Story 3's listener ownership, profile data does not need cross-instance consistency to satisfy the spec — each instance independently caching for 60s is sufficient because (a) the source investigation's own recommended range was 30-60s per-instance, (b) a profile lookup is not part of a coordination protocol other instances depend on, and (c) introducing Redis for this would violate Simplicity (Principle V) for no measurable benefit beyond what a local `Map` already provides.

**Alternatives considered**:
- *No TTL, invalidate-only cache* — rejected: would require every possible external Firestore write path (including any future one) to remember to invalidate, a fragile invariant; a bounded TTL caps the blast radius of a missed invalidation to 60s, matching the accepted staleness window in `FR-003`.
- *HTTP ETag / conditional caching* — rejected: adds complexity (client-side cache-aware requests) disproportionate to the problem; the redundant reads originate server-side (`/join` calling `resolveDisplayName` alongside other paths), not from repeated client GETs.

## §3. Typing-status sweep interval (Story 2)

**Current state**: `server/src/adapters/firebase/FirestoreRealtimeGatewayAdapter.ts` runs `setInterval(() => sweepStaleTyping(id), 500)` per board with ≥1 connection, unconditionally querying Firestore every 500ms regardless of whether anyone is typing. `TYPING_STATUS_TTL_MS = 3000`.

**Decision**: Make the sweep **event-driven** rather than a fixed unconditional poll: only (re)schedule a sweep check when the `typingStatus` Firestore listener itself has actually observed a write (i.e., inside the existing `watchCollection(retrospectiveId, TYPING_STATUS, 'typingStatus')` `onSnapshot` callback, schedule one `sweepStaleTyping` call ~`TYPING_STATUS_TTL_MS` after the observed write, via `setTimeout`, instead of an unconditional `setInterval`). This preserves the ≤3.5s worst-case indicator-clear latency (`SC-002`) — the timer is now anchored to the *actual* stale-write event instead of firing blindly every 500ms whether or not there's anything to check — while eliminating the constant 120 reads/minute/board/instance cost when no one is typing.

**Alternatives considered**:
- *Simply lengthen the interval (e.g., 500ms → 2s)* — rejected as the sole fix: still polls unconditionally 24/7 even with zero typing activity across the board's entire lifetime (just less often), and a longer fixed interval risks missing `SC-002`'s ≤3.5s clear-latency target on the worst-case single check. The event-driven approach eliminates the background cost entirely when idle rather than just reducing its frequency, better satisfying `FR-004`'s "no longer a fixed, always-on cost" requirement.
- *Client-driven expiry (rely on the client's own 3s inactivity timeout to send an explicit "stopped typing" write)* — rejected: the existing code comment already documents this TTL sweep as the server-enforced backstop specifically for the case where a client disconnects *without* sending that explicit stop (network drop, tab close) — removing the server-side sweep entirely would reopen that gap (feature 026 regression risk), which the Assumptions section explicitly rules out touching.

## §4. Multi-instance listener coordination — Redis client selection (Story 3)

**Requirement**: A shared, external coordination mechanism (per `FR-008`) that supports (a) an exclusive, renewable, expiring lock per board (for ownership) and (b) low-latency message delivery from the owning instance to every other instance currently serving that board (to relay Firestore-derived events, since only the owner instance runs the actual `onSnapshot` listeners).

**Decision**: **`ioredis`** (npm, actively maintained, ~15M weekly downloads, MIT license, first-class TypeScript types, already the de facto standard Node.js Redis client used against Upstash's Redis-protocol endpoint) connected to an **Upstash Redis** database provisioned through the Vercel Marketplace free tier, per the stakeholder's stated preference. Upstash provisions both a REST endpoint and a standard Redis-protocol (RESP) connection string; the RESP connection is required here because Redis Pub/Sub (`SUBSCRIBE`/`PUBLISH`) is not exposed over Upstash's REST API — only the RESP protocol supports it.

**Rationale**:
- Holding one persistent `ioredis` connection per active backend instance is architecturally consistent with what this codebase already does for Firestore: `FirestoreRealtimeGatewayAdapter` already holds long-lived `onSnapshot` listener connections per instance for the lifetime of the boards it serves. Adding one more long-lived connection (to Redis instead of/alongside Firestore) is not a new class of resource-lifecycle risk for Fluid Compute, which keeps instances warm across requests rather than tearing them down per-invocation.
- Redis connection ceilings (even on free tiers) are a documented, fixed numeric limit tied to concurrent instance count — not the opaque, traffic-shape-sensitive anti-abuse throttle that caused the original incident. Moving the "N instances = N connections" pattern from Firestore (where it triggered undocumented abuse protection) to Redis (where the limit is a known, fixed, and generous number relative to this app's realistic concurrent-instance count) is the entire point of this story.
- Satisfies Constitution Principle III (Prefer Proven Third-Party Libraries): `ioredis` is established, actively maintained, and not duplicating any existing in-repo capability.

**Alternatives considered**:
- *`@upstash/redis` (REST-only SDK)* — rejected as the sole client: cannot support `SUBSCRIBE`, which this story structurally requires for cross-instance event relay. It remains a reasonable choice for simple key GET/SET-style operations if a future need arises, but the coordination protocol here (lock + pub/sub) needs RESP.
- *A different external store entirely (e.g., a lightweight database table for locks + Server-Sent polling for relay)* — rejected: reintroduces exactly the kind of polling-driven read amplification this whole feature is trying to eliminate, and does not match the stakeholder's explicit Redis preference.
- *Vercel Queues* — considered as a pub/sub-like relay alternative; rejected for this use case because it is designed for durable at-least-once task delivery, not low-latency fan-out broadcast to N live WebSocket-holding instances, and would add operational complexity (queue consumer per instance, per board) beyond what a Redis channel already provides simply.

## §5. Board-listener ownership protocol (Story 3)

**Decision**: A per-board **lease-based lock** in Redis:
- Key: `board-owner:{retrospectiveId}` → value: an opaque instance identifier (e.g., a UUID generated once per process boot).
- Acquired with `SET key instanceId NX PX <leaseMs>` (atomic set-if-absent with expiry), triggered by **two** independent events: (a) when an instance registers the *first* local WebSocket connection for a board it does not already own, **and** (b) periodically, on the same cadence as the heartbeat renewal below, for as long as an instance has ≥1 local connection for a board it does not currently own.
- Renewed via a periodic heartbeat (interval = leaseMs / 3) for as long as the owning instance still has ≥1 local connection for that board, using a compare-and-renew Lua script (`GET` then conditionally `PEXPIRE`/`SET` only if the stored value still matches this instance's id) to avoid an instance renewing a lock it no longer actually holds (e.g., after a lease already expired and another instance took over).
- Released (deleted, if still owned by this instance) when the last local connection for that board unregisters — mirroring the existing reference-counted teardown already present in `FirestoreRealtimeGatewayAdapter.unregister()`. No explicit hand-off notification accompanies release; recovery is entirely trigger (b)'s responsibility (see below).
- If the lease expires without renewal (instance crash, hard kill without a clean `unregister`), the key simply expires; the next instance with a local connection to that board that attempts to acquire it succeeds via the same `NX` check, satisfying `FR-007`'s "responsibility transfers ... without participants missing real-time updates" (bounded by the lease duration — see quickstart.md for the concrete acceptance check).

**Why trigger (b) is required, not optional** (closing a gap found during `/speckit-analyze`): trigger (a) alone only covers hand-off when the crash/lease-expiry happens to coincide with, or precede, a *new* registration on a surviving instance. It does **not** cover the equally realistic case where the owner *gracefully* releases (its own last local connection unregisters) while a *different* instance already has active local connections to that same board from earlier — that instance has no new registration event to hang an acquire attempt on, and without trigger (b) it would be left as a subscriber to a channel nobody publishes to, silently losing real-time delivery for its connected participants. Trigger (b) closes this by making every non-owner instance with local connections a periodic self-healing candidate, on the same heartbeat cadence already used for renewal — no new message type or push-style hand-off notification needed.

**Alternatives considered**:
- *Redlock-style multi-node consensus locking* — rejected as unnecessary complexity: this app's Redis is a single logical Upstash database (not a self-managed multi-primary Redis cluster the app needs to reason about split-brain for), so a single-key `SET NX PX` lease with a compare-and-renew script is sufficient and matches Simplicity (Principle V).
- *Push-style hand-off notification (owner publishes a "relinquishing" message on release)* — rejected in favor of trigger (b)'s pull model: a push notification would need reliable delivery to every subscriber (itself a hard problem — the departing owner could crash mid-publish), whereas periodic self-checking is trivially reliable (worst case, bounded by one heartbeat interval) and reuses infrastructure (the heartbeat timer) this adapter already has, rather than introducing a second coordination primitive.

## §6. Cross-instance event relay (Story 3)

**Decision**: A Redis Pub/Sub channel per board, `board-events:{retrospectiveId}`. Split the existing `FirestoreRealtimeGatewayAdapter`'s two responsibilities:
1. **Firestore→Redis (owner only)**: only the instance currently holding the `board-owner:{retrospectiveId}` lease runs the actual `onSnapshot` listeners (today's `startWatch()` logic, unchanged) and, instead of broadcasting directly to its own local `connections` set, `PUBLISH`es each translated `RealtimeEvent` (the exact same JSON shape `toEntityChangeEvent` already produces) to `board-events:{retrospectiveId}`.
2. **Redis→local connections (every instance)**: every instance with ≥1 local connection for a board `SUBSCRIBE`s to that board's channel and, on message, applies the existing per-connection visibility filter (`isVisibleToConnection`, unchanged — still needed for `facilitatorNote` scoping) and delivers to its own local WebSocket connections only. The owning instance also subscribes to its own channel like any other instance, so it needs no special-cased local delivery path — one code path handles delivery everywhere.

This is purely a routing change: the wire-level `RealtimeEvent` JSON schema delivered to browsers is unchanged (`FR-009`, `FR-010`), so `contracts/realtime-protocol.md` from feature 019 (if referenced) requires no revision — see `contracts/redis-coordination-protocol.md` in this feature for the new *internal* (server-to-server) channel/lock schema this introduces.

## §7. Fail-open behavior (per clarification, `FR-008a`)

**Decision**: Wrap every Redis operation (lock acquire/renew/release, publish, subscribe) with a short timeout and a circuit-breaker-style state per board: if a Redis operation for a board fails or times out, that instance immediately falls back to running its own direct `FirestoreRealtimeGatewayAdapter`-style local listeners for that specific board (today's exact behavior — the pre-existing, already-shipped code path, simply left un-torn-down / re-instantiated), independent of any other instance's state, and marks that board "degraded" locally. On a fixed retry cadence (e.g., every 10-30s) while any board is in the degraded set, the instance attempts to re-acquire normal Redis coordination for that board; on success it tears down the temporary direct listener and resumes the coordinated (owner/subscriber) mode. Because each instance decides this independently per board, no global "is Redis up" flag or cross-instance agreement is needed for the fallback itself — only the *return* to coordinated mode benefits from Redis being reachable again, which is naturally self-healing once it is.

**Why this satisfies the clarification**: the fallback path is literally "run the code this repo already ships today," which is the lowest-risk possible degraded mode — it cannot regress below the *current* production behavior, only potentially reintroduce the current behavior's known cost (duplicate listeners across instances) for the duration of the Redis outage, which is explicitly accepted as the tradeoff.

## §8. Dead-code removal (`FR-011`)

**Confirmed**: `FirestoreTypingStatusAdapter.listActive()` (`server/src/adapters/firebase/FirestoreTypingStatusAdapter.ts`) has zero real call sites across `server/src` and `retro-rocket/src` (grep-verified). It appears only in: its own implementation, its declaration on the `TypingStatusPort` interface (`server/src/application/ports/typing.ts`), and as a required-by-the-interface stub in three test fakes/mocks (`server/test/http/routes/retrospectives.test.ts`, `server/test/application/use-cases/retrospective/SetTypingStatus.test.ts`, `server/test/application/use-cases/retrospective/retrospectiveFakes.ts`) — none of which ever invoke it, they only satisfy the port's TypeScript shape. Removing both the method and its `TypingStatusPort` interface declaration will let those stubs be deleted too. Safe to remove per the Assumptions section's "zero call sites" bar. No other dead periodic/cron work was found beyond the sweep already addressed in §3.
