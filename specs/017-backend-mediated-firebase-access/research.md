# Phase 0 Research: Backend-Mediated Firebase Access

## 1. Real-time transport: Server-Sent Events over a Firestore Admin SDK relay

**Decision**: Each connected client opens one `GET /api/boards/:id/events` request per board using the browser's native `EventSource` API. On the backend, that request handler subscribes to the same Firestore collections/queries the frontend used to listen to directly (via `firebase-admin`'s real-time listener support — the Admin SDK supports `.onSnapshot()` the same way the client SDK does), and forwards each change as an SSE event (`event: card.updated`, `data: {...}`). All writes (create/edit/delete/like/react/group/etc.) are separate, ordinary REST calls (`POST`/`PATCH`/`DELETE`) — the SSE channel is receive-only.

**Rationale**:
- **Zero new dependencies.** `EventSource` is a native browser API; Express can stream a `text/event-stream` response with plain `res.write()`. No `ws`, no Socket.IO, no third-party realtime service needs to be added, directly satisfying Constitution Principle III (prefer proven libraries — here, prefer *no* library) and Principle V (Simplicity/YAGNI: a full-duplex WebSocket is unnecessary because the frontend never needs to push arbitrary data over the same channel it receives updates on).
- **Free reconnect semantics.** `EventSource` automatically reconnects (with backoff) whenever its underlying connection drops, with zero custom client code. This directly satisfies spec FR-011 ("clearly surface a disconnected/reconnecting state and automatically resume real-time sync") using a well-tested platform primitive instead of hand-rolled WebSocket reconnect logic.
- **Fits the serverless duration constraint.** Vercel functions currently cap execution at 300s. A long retro session will therefore cause the backend to close the SSE stream well before the session ends. Because `EventSource` reconnects transparently, this becomes an invisible, automatic ~5-minute reconnect cycle rather than a special case the frontend needs to detect and handle differently from a genuine network blip — both are "the stream closed, reconnect," and FR-011 already scopes the requirement to "best-effort reconnect," so a periodic function-imposed reconnect is within scope, not a gap.
- **Correctness across horizontally-scaled serverless instances.** Because Fluid Compute may run multiple concurrent instances of the same function, an in-process pub/sub (e.g., an in-memory map of connected clients per board) would not reliably fan out an update made on one instance to a client connected to a different instance. Using Firestore itself (via the Admin SDK's real-time listener) as the shared source of truth and fan-out mechanism sidesteps this entirely: every SSE connection, regardless of which instance handles it, independently listens to Firestore and will observe the same writes. This also matches the spec's Assumption that "the existing Firestore data model and collections are reused as-is."
- **Alternative considered — WebSocket via Vercel Functions.** Vercel Functions now support WebSockets under Fluid Compute. Rejected for v1: it would require a new client-side dependency or hand-rolled protocol for messages that, in this app, only ever flow server→client; adopting a duplex protocol for a one-directional need is unjustified complexity per Principle V. Revisit only if a genuine bidirectional low-latency need emerges (e.g., cursor-sharing) that SSE cannot serve.
- **Alternative considered — client-side polling.** Rejected: adds baseline request volume proportional to open boards × poll interval, and cannot beat the "instant" feel (SC-003, 2s) as cleanly as a push-based stream without polling aggressively enough to erase the simplicity benefit.
- **Alternative considered — a third-party realtime service (Pusher/Ably/etc.).** Rejected: introduces a new paid dependency and a second real-time system to keep consistent with Firestore, when Firestore's own real-time capability is already present, proven in this codebase (used server-side today for nothing yet, but the client SDK equivalent has powered every real-time feature in production), and sufficient.

**Design notes carried into data-model.md / contracts**:
- One Firestore listener per relevant collection/query per SSE connection is the v1 design (simplicity first). A shared per-board listener multiplexer (one Firestore listener feeding N SSE connections on the same board within the same function instance) is a valid future optimization if listener count becomes an operational concern, but is explicitly **not** built now (YAGNI) — nothing in the spec requires it, and it adds a stateful in-memory registry the simple design avoids.
- Facilitator-only events (facilitator notes) must only be written into the SSE stream belonging to the requesting user's own connection if that user is the board's facilitator — enforced at the relay layer (a domain-level `canIncludeFacilitatorNotes`-style check, mirroring the existing MCP pattern at `server/src/domain/mcp/FacilitatorAccess.ts`), not left to the client to filter.
- Typing-status indicators continue to be persisted to Firestore (as today) rather than moved to purely in-memory ephemeral state, specifically so the same "Firestore as shared fan-out" design handles them consistently — see data-model.md.

## 2. Firestore security rules: current state is weaker than it looks

**Finding**: `firestore.rules:8-10` defines a global catch-all — `match /{document=**} { allow read, write: if request.auth != null && ...sign_in_provider != 'anonymous'; }` — before any of the more specific per-collection rules. Firestore evaluates *all* matching `match` blocks for a given path and grants the operation if *any* matching block allows it. Because the catch-all unconditionally grants read+write to any authenticated non-anonymous user for every path, the more specific ownership rules for `countdown_timers` (creator-only write), `facilitatorNotes` (facilitator-only read/write), and `actionItems` (facilitator-only write) are **currently dead code** — any authenticated user can already read/write these collections directly today via the client SDK, bypassing the intended per-role restrictions. Only the three MCP collections (`mcpClients`, `mcpAuthorizationCodes`, `mcpConnections`, added in feature 015) are genuinely locked down, via explicit `allow read, write: if false` with no competing catch-all-style grant.

**Decision**: The backend's new authorization logic (domain-level checks in `server/src/domain/boards/`) must enforce the *intended* rules — the ones expressed in the specific-but-currently-ineffective match blocks, matching the product's documented behavior (README: "Facilitator notes stay private," countdown is facilitator-controlled) — not the accidentally-permissive effective behavior. This is exactly what spec FR-004 already specifies. Once the frontend has zero direct Firestore access, `firestore.rules` for the migrated collections should be tightened to `allow read, write: if false` (mirroring the MCP collections), closing the catch-all loophole for real. This is a **strengthening** of the security posture (a previously-real gap gets closed), not a weakening, and satisfies the constitution's requirement that any `firestore.rules` change be justified — the justification is exactly this refactor's purpose plus the discovery documented here. This must be called out explicitly in the implementing PR description.

**Alternatives considered**: Leaving `firestore.rules` as-is post-migration (rejected — pointless residual attack surface once the backend is the only intended caller; an attacker with a stolen/forged Firebase ID token would still have direct read/write access) vs. tightening only the three collections that had real intended restrictions vs. tightening all migrated collections to `if false` (chosen — once nothing legitimate calls Firestore from the client, there is no reason to leave *any* collection open, and a single uniform "backend Admin SDK only, no exceptions" rule is simpler to reason about and audit than a per-collection mix).

## 3. Reconciling triplicated retrospective CRUD logic

**Finding**: Retrospective create/read/update/delete/list logic currently exists in three overlapping places with divergent behavior: `retrospectiveService.ts` (hard delete, cascades to `participants`+`cards` only), `OptimizedRetrospectiveService.ts` (soft-delete variant, narrower hard-delete that doesn't cascade at all, plus dead code querying a `facilitator` field that nothing ever writes — real field is `createdBy`), and `userService.getUserBoards` (the dashboard's "list my boards" query, merging owned + joined boards client-side).

**Decision**: The new backend exposes exactly one canonical set of board operations (`POST /api/boards`, `GET /api/boards`, `GET /api/boards/:id`, `PATCH /api/boards/:id`, `DELETE /api/boards/:id`, `POST /api/boards/:id/join`), each backed by one use-case. `DELETE /api/boards/:id` performs a **hard delete with a complete cascade** — including `groups`, `actionItems`, `facilitatorNotes`, `sentimentResults`, `countdown_timers`, `typingStatus`, and the `columns` subcollection, none of which any current implementation fully cleans up. This is a data-hygiene fix that fits within "no functionality lost" (the user-visible outcome — "my deleted board and its data are gone" — is what users already expect and is what the product documentation implies; nothing user-facing regresses) rather than a new requirement. Soft-delete is **not** carried forward: nothing in the spec or the product's documented behavior (README/usage guide) describes a trash/restore UI, `OptimizedRetrospectiveService`'s soft-delete path appears to be unused dead code (its `facilitator`-field queries never match real data), and introducing a user-facing restore feature would be new scope, not a refactor. If a restore/trash capability is wanted, that is a separate, explicitly-scoped future feature.

**Alternatives considered**: Preserving both hard and soft delete as two backend endpoints (rejected — no evidence either the UI or users rely on soft-delete/restore today; carrying forward apparently-dead functionality violates Simplicity/YAGNI) vs. hard delete without full cascade (rejected — perpetuates an existing data-hygiene bug into new code for no reason, when fixing it costs nothing extra at this layer).

## 4. Reconciling duplicate typing-status implementations

**Finding**: `typingStatusService.ts` and `OptimizedTypingStatusService.ts` are two independent, parallel implementations writing to the same `typingStatus` collection (one with a 6s client-side staleness window, one with a 300ms debounce and 5s window), both still in the source tree.

**Decision**: One canonical typing-indicator flow is exposed: `POST /api/boards/:id/typing` (fire-and-forget, board+column+user scoped) writes/refreshes a `typingStatus` document server-side with a short TTL semantic, relayed to other connected clients over the board's SSE stream. The 300ms debounce behavior (the newer/optimized implementation's improvement over the older one) is preserved, but implemented once, client-side, before the API call is made (debouncing is a UI-responsiveness concern, not something that needs to exist twice or move server-side). The older `typingStatusService.ts` implementation's behavior (hardcoded 3-column cleanup that doesn't generalize to dynamic templates) is **not** carried forward — it is treated as a bug being fixed, not a behavior being preserved, since the "no functionality lost" mandate concerns user-visible behavior (typing indicators work correctly for whatever columns a board actually has), not the specific buggy implementation detail.

## 5. Non-atomic operations become atomic

**Finding**: Several current operations are read-then-write races or falsely-batch-like sequences of independent writes: `cardService.voteCard` (read current value, compute, write — no transaction), `cardInteractionService.addOrUpdateReaction`/`batchUpdateCardOrder` (sequential individual writes presented as if atomic), `cardGroupService`'s group mutations (these *do* correctly use Firestore `writeBatch`, the one part of the current code already atomic).

**Decision**: Moving these operations behind backend use-cases is the natural point to make them properly atomic using Firestore transactions/batched writes (available identically via the Admin SDK). This closes existing race-condition risk as a byproduct of the migration, consistent with spec FR-014's last-write-wins conflict policy for whole-document concurrent edits — the atomicity fix is about a *single* logical operation (e.g., "toggle my like") being internally consistent, which is a prerequisite for FR-014 to even be meaningful (last-write-wins only makes sense for well-defined, atomic writes).

## 6. Frontend auth/profile bootstrap moves fully server-side

**Finding**: `UserContext.tsx` currently orchestrates `bootstrapSession()` (backend) followed by three separate calls into `userService` (`getUserProfile`/`createUserProfile`/`addProviderToUser`) to keep the Firestore `users/{uid}` profile document in sync with the backend's OAuth-derived provider list — this is exactly the kind of frontend→Firestore write this refactor eliminates.

**Decision**: Profile bootstrap (create-if-missing, provider-list sync) moves entirely into the existing `CompleteOAuthLogin` use-case (`server/src/application/use-cases/CompleteOAuthLogin.ts`), which already runs server-side on every successful OAuth callback and already has the definitive provider/uid information. The frontend's session-fetch response (`GET /api/auth/session`) is extended to include the full profile shape the UI needs (display name, photo, linked providers) so `UserContext` no longer needs any separate profile call at all, let alone a direct Firestore one. `userService.ts` is retired; `UserProfileCache.ts` (used by the participants UI to batch-resolve other users' display names/photos) is replaced by a small backend endpoint (`GET /api/boards/:id/participants` already returns resolved profile fields, so a separate profile-cache round-trip is unnecessary — see data-model.md).

## 7. E2E test strategy after the cutover

**Finding**: `e2e/fixtures/auth-helpers.ts:6-16` already authenticates via the backend's `POST /api/auth/test-login` (an `AUTH_TEST_MODE`-gated endpoint), then relies on the resulting Firebase custom token being consumed client-side (`signInWithCustomToken` against the Auth Emulator) purely so the client SDK's direct Firestore reads keep working during the test run.

**Decision**: Once no frontend code performs direct Firestore reads/writes, the custom-token-to-Auth-Emulator step in `bootstrapSession()`/`UserContext` is deleted (per FR-006/FR-010), and E2E tests need only the backend session cookie set by `test-login` — no client-side Firebase Auth involvement at all. The Firebase Emulator Suite is still needed in CI (`npm run e2e` invokes `firebase emulators:exec --only auth,firestore ...`) so the **backend's** Admin SDK has a Firestore emulator to talk to; the `auth` emulator can likely be dropped from that command once nothing in the browser touches Firebase Auth, but this is left as a task-level cleanup rather than a plan-level decision, since it's a CI-config detail with no functional impact either way.
