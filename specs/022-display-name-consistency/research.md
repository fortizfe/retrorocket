# Research: Consistent Display Name Resolution Across the App

**Feature**: [spec.md](./spec.md)

## 1. How should a rename reach every surface, including boards already open by other participants (FR-007, SC-002)?

**Decision**: On `PATCH /api/profile` (rename), after writing `users/{uid}.displayName`, fan out and update the `name` field on every `participants` document where `userId == uid`, across all retrospectives the user has ever joined. Do not add any new realtime event type, WebSocket channel, or batch profile-read endpoint.

**Rationale**: `server/src/adapters/firebase/FirestoreRealtimeGatewayAdapter.ts` already runs a per-board, reference-counted Firestore listener on the `participants` collection (`watchCollection(retrospectiveId, PARTICIPANTS, 'participant')`, scoped `where('retrospectiveId', '==', retrospectiveId)`) for every board that has at least one open WebSocket connection, and already broadcasts any `modified` change as a wire `{ entity: 'participant', op: 'updated', data }` event to every connection on that board. The frontend's `applyEntityChange` reducer (`useRetrospectiveRealtimeSync.ts`) already handles `'participant'`/`'updated'` generically via `upsertById`. So a plain Firestore write to an existing `participants` doc's `name` field is, with zero new code on the realtime path, delivered live to every other participant currently viewing that board — exactly the guarantee `019`/`021` already built and tested (2s p95). Building a new push mechanism (new WS event type, new per-user connection index, or a client-polled batch profile endpoint) would duplicate infrastructure the app already has, violating Simplicity/YAGNI (Principle V) and the precedent `021`'s own plan set by explicitly rejecting new endpoints/ports when existing data already covered the need.

**Alternatives considered**:
- *New `entity: 'profile'` WS event, broadcast to every board a user currently has open*: rejected — the gateway's connection registry (`FirestoreRealtimeGatewayAdapter.boards: Map<retrospectiveId, BoardWatch>`) is keyed per-board, not per-uid-globally; broadcasting to "every board this user has open right now" would require a new cross-board connection index that does not exist today. More moving parts for no behavioral gain over the fan-out approach.
- *New backend batch endpoint (`GET /api/profiles?uids=...`) queried by the frontend on every board load/refresh*: rejected as the primary mechanism — it would need to be polled or paired with its own push signal to satisfy "live, no reload" (FR-007), effectively re-deriving the participant-fan-out design one layer higher, with added latency and a new port/route/contract surface. (A batch endpoint would also read `users/{uid}` for arbitrary other users, which is a new sensitive-data exposure surface — see §5 — that the fan-out design avoids entirely by never exposing more than a name update through data already scoped to a board.)

## 2. What is the authoritative source for a card/like/reaction/participant's "currently configured" name (FR-001, FR-001a)?

**Decision**: The board's own `participants` array, kept synchronized with the account's current display name via the write-time fan-out in §1, is the resolution source — checked *first*, ahead of the name captured at creation/interaction time. This satisfies FR-001a's requirement without adding a second, independent profile-lookup layer.

**Rationale**: Every author of a card, like, reaction, or participant entry on a given board is guaranteed to already have a `participants` doc for that exact `retrospectiveId` — `useRetrospectiveRealtimeSync`'s `joinBoard()` call fires on every (re)connect to a board (`RetrospectivePage.tsx`), before any card/like/reaction interaction is possible, and `JoinRetrospective`/`FirestoreRetrospectiveBoardAdapter.join()` is idempotent and creates that doc if missing. Once §1's fan-out keeps that doc's `name` field synchronized with `users/{uid}.displayName` for as long as the account exists, checking the board's own `participants` array *is* checking the current account/profile — just via a copy that is kept fresh at write time instead of read time. The two are behaviorally equivalent for every surface this feature covers (all of which are board-scoped), so FR-001a's underlying concern — "a board-local record MUST NOT be trusted as authoritative for 'current' if it can go stale" — is resolved at the source (the record no longer *can* go stale while the account exists), not by adding a second lookup path.

**A useful, free side effect**: once the account is deleted, fan-out simply stops. The `participants.name` field is not otherwise touched, so it automatically freezes at the last value it was fan-out-updated to — which is precisely FR-003/FR-004's desired "captured/last-known name" fallback behavior, with no explicit "does this account still exist" check required anywhere in the resolution code.

**Alternatives considered**:
- *New `ProfilePort.getProfiles(uids: string[])` batch method + a resolve-time lookup, independent of `participants`*: this was the initial hypothesis before finding `019`'s existing per-board Firestore-to-WebSocket relay. Rejected once §1 showed it would duplicate work the fan-out design gets for free, and because it introduces a new endpoint that must decide what subset of `ProfileRecord` (which includes `email`) is safe to expose to other participants — an unnecessary new privacy-review surface (§5) the fan-out design avoids by never serving another user's profile data directly, only a name already implicitly visible to board co-participants.

**Boundary condition this decision depends on**: every card/like/reaction author must already be a participant of that same board. This holds today because `joinBoard()` is called automatically before any board interaction and no "leave board" / participant-removal feature exists. If a future feature ever allows creating a card without first joining, or removes/purges old participant docs, this decision must be revisited.

## 3. Should the session-cached name used to capture `createdByName`/`username` at write time (`displayNameOf(session.user)`) be changed to read live from Firestore?

**Decision**: No change. Leave `displayNameOf(session.user)` (`server/src/http/routes/retrospectives.ts`) as-is.

**Rationale**: `displayNameOf` reads the OAuth-login-time-cached name off the session cookie, not the live `users/{uid}.displayName` — so if a user renames via Profile and then immediately creates a new card without a fresh login, the newly *captured* `createdByName` could reflect the pre-rename name. This is a real, pre-existing inconsistency, but per §2's resolution order it is harmless: the captured name is only ever consulted as a fallback when no matching `participants` doc exists, and every new card's author always has one (§2's boundary condition). Fixing `displayNameOf` to read Firestore live on every card/like/reaction/join write would add a new synchronous Firestore read to already-latency-sensitive write paths for a value that resolution never actually surfaces in practice — a violation of Simplicity/YAGNI for a bug with no observable effect under this feature's corrected resolution order. Documented here so it isn't silently rediscovered; not carried into `tasks.md`.

## 4. How does "account no longer exists" get simulated for testing (FR-003/FR-004, User Story 2), given account deletion isn't built yet?

**Decision**: No account-deletion capability is built as part of this feature. `retro-rocket/src/pages/Profile.tsx`'s "Eliminar cuenta" button is a hard-`disabled` placeholder today, and no backend route, use case, or `ProfilePort` method for deletion exists. Per §2, this feature doesn't need one either — "deleted" resolves to the same code path as "this specific participant record was never fan-out-updated again," which is directly reproducible in tests by seeding a `participants` doc (or a card/like/reaction) whose `userId` has no corresponding `users/{uid}` doc and never receives a fan-out write, exactly mirroring the test-fixture technique `020-user-display-name-fix` already used for its own "legacy card, unknown author" scenario.

**Rationale**: The user's feature request is about display-name resolution, not about shipping account deletion — building it would be unrequested scope expansion. The resolution algorithm designed in §2 is deletion-mechanism-agnostic (it doesn't check "does the account exist," it checks "is there a fresher name than what was captured," which degrades correctly regardless of *why* no fresher name is arriving).

## 5. Is a new backend surface needed to read another user's current name (batch or otherwise)?

**Decision**: No. §1/§2 together mean this feature adds no new read endpoint. The only new backend capability is a write-side fan-out triggered from the existing `PATCH /api/profile` handler.

**Rationale**: `server/src/application/ports/profile.ts`'s `ProfilePort` has only `ensureProfile` (get-or-create for the caller's own session identity) and `updateDisplayName` — no batch/multi-uid read exists, and building one would (a) duplicate the fan-out design's job and (b) require deciding what part of `ProfileRecord` (which bundles `email`) is safe to expose about *other* users, which the fan-out design sidesteps entirely by only ever propagating a name into a collection (`participants`) that board co-participants can already read in full today.

**Noted but out of scope**: `firestore.rules` has no rule block for `users/{uid}` at all — it falls through to the top-level authenticated-non-anonymous catch-all, meaning any signed-in client can today read (and write) any other user's full profile doc (including email) directly via the Firestore client SDK, bypassing the backend entirely. This is a pre-existing gap from the `018`/`021` backend-migration work, not introduced or worsened by this feature (which adds no new client-side Firestore reads of `users/*`), and fixing it is unrelated to display-name resolution. Flagged here for visibility, not carried into `tasks.md`.

## 6. Do likes and reactions already capture a name at write time (FR-002)?

**Decision**: No new capture work needed. `toggleLike`/`setReaction` (`server/src/application/use-cases/retrospective/CardInteractions.ts`, called from `server/src/http/routes/retrospectives.ts`) already persist `username: displayNameOf(session.user)` server-side, exactly mirroring how cards capture `createdByName` (`020`). `JoinRetrospective` likewise already persists `name: userName` (server-derived) on the participant doc. FR-002 is already satisfied for every entity type; this feature only changes how those captured values are *prioritized* at display time (§2), not how/whether they're captured.

## 7. Where does the raw-uid leak actually occur today, and what do the fixes look like?

**Decision**: Three concrete, independent display-time gaps, all fixed by generalizing and correctly prioritizing the existing `resolveAuthorDisplayName` helper (see data-model.md):

1. **Exports** — `txtExportService.ts:736-737`, `pdfExportService.ts:593`, `docxExportService.ts:907-908` each interpolate `card.createdBy` (the raw uid) directly into "Autor: …" output, never calling the resolver at all, despite `card.createdByName` already being in scope and the file's own doc comment ("resolve those via `resolveAuthorDisplayName`, never render `createdBy` directly") already saying not to do this. The exporters' own option-type declarations for `participants` (`Array<{ name: string; joinedAt: Date }>`) are narrower than the real `Participant` type actually passed in at the one real call site (`RetrospectiveTopbar.tsx` → `ImprovedExportPopover.tsx`, which forwards the full `Participant[]` including `userId` — present at runtime today, just not typed) — so enabling resolution here is a type-widening plus a call to the resolver, not new data plumbing.
2. **Likes/reactions** — `LikeButton.tsx` and `EmojiReactions.tsx` are purely presentational and render `like.username`/`reaction.username`/`GroupedReaction.users` (raw captured values) directly; neither ever consults `participants`, so a like/reaction tooltip never reflects a post-interaction rename. Fixed by threading `participants` down from `DraggableCard.tsx` (which already receives it, for the card author label) and resolving through the shared helper.
3. **`GroupedReaction.users`** (`cardHelpers.ts`'s `groupReactions()`) collapses `Reaction[]` into `{ emoji, count, users: string[] }`, pushing `reaction.username` and discarding `reaction.userId` in the process — so grouped-reaction display can only ever show the captured name, never a resolved current one, and (found incidentally while tracing this) `EmojiReactions.tsx`'s own-reaction detection (`reaction.users?.includes(currentUserId)`) is comparing a uid against an array of *usernames*, a latent pre-existing bug (the current user's own reaction pill is never correctly detected as "mine"). Fixed by adding a parallel `userIds: string[]` field to `GroupedReaction` (populated from `reaction.userId`) alongside the now-resolved `users: string[]`, which both enables correct display resolution and fixes the self-reaction-detection bug as a natural side effect of touching this exact code — not a separate initiative.

**Rationale for generalizing rather than duplicating**: `resolveAuthorDisplayName` today takes a `Pick<Card, 'createdBy' | 'createdByName'>`, so it's unusable for likes/reactions/exports as-is. Generalizing its signature to `resolveDisplayName(userId, capturedName, participants, fallbackLabel)` — accepting a bare `userId`/`capturedName` pair instead of a `Card` — lets all five call sites (card author label, group header, like tooltip, reaction tooltip, and the three export services) share one implementation of the resolution order defined in §2, satisfying FR-005's "no two surfaces ever disagree."
