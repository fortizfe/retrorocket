# Quickstart: Validating the Landing Page Redesign

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This is a validation guide, not an implementation guide — it documents how
to run and manually/automatically verify the redesigned landing page once
implemented. See `data-model.md` and `contracts/` for what "correct" means;
see `tasks.md` (generated by `/speckit-tasks`) for how to build it.

## Prerequisites

- Repo dependencies installed: `cd retro-rocket && npm install`
- Firebase emulators available for auth/Firestore-backed flows (used by E2E,
  not required for a pure visual check): `npm run emulators` (separate
  terminal), or rely on `npm run e2e` which starts them automatically.

## 1. Run the page locally

```sh
cd retro-rocket
npm run dev
```

Open `http://localhost:5173/` (or the port Vite prints) unauthenticated.

**Check**:
- Hero and primary sign-in CTA are visible without scrolling, at a common
  desktop width (~1280-1440px), a common tablet width (~768-834px), and a
  common mobile width (~375-414px) — verify with browser devtools device
  toolbar (FR-006, FR-007, SC-001).
- No literal product screenshots/UI mockups anywhere on the page — abstract/
  typographic/motion treatment only (FR-001).
- Toggle the theme control — every section stays legible in both light and
  dark themes (FR-004, US2 Acceptance Scenario 3).
- Switch the browser/OS language between English and Spanish (or use the
  in-app language selector if present) — all text renders correctly, no
  raw `landing.*` key strings visible, no layout breakage from differing
  text lengths (FR-003, US3 Acceptance Scenario 2).
- In devtools, enable "Emulate CSS prefers-reduced-motion: reduce" — scroll
  through the page; all content is still fully readable/usable, no motion
  required to access anything (FR-005, US2 Acceptance Scenario 2).
- Throttle the network (devtools → Network → Slow 3G) and reload — confirm
  content progressively fades/reveals in as it becomes ready; there is no
  blank hold and no skeleton/placeholder UI (FR-011).

## 2. Verify the sign-in flow still works end-to-end

With the Firebase auth emulator running:

1. Click "Sign in with Google" (or GitHub) — the existing OAuth flow
   completes exactly as before (FR-002).
2. On first sign-in, the display-name setup step appears, styled using the
   new design system (US3 Acceptance Scenario 1); saving a name proceeds to
   the dashboard.
3. Manually append `?auth_error=access_denied` to the landing URL and reload
   — confirm the corresponding error toast still surfaces, styled to match
   the new design (Edge Cases, FR-002).
4. While already signed in, navigate back to `/` — confirm the existing
   redirect-away-from-landing behavior still fires (Edge Cases, FR-002).

## 3. Automated checks

```sh
cd retro-rocket

# Type-check and lint
npm run type-check
npm run lint

# Unit/component tests + coverage gate (branches 78 / functions 64 / lines 50 / statements 50)
npm run test:coverage

# If any new/changed design tokens were introduced, confirm WCAG contrast math still holds
npx vitest run src/test/lib/theme/contrast.tokens.test.ts --config vitest.config.ts

# E2E: authentication + accessibility (WCAG 2.1 AA, both themes, keyboard tab order)
npm run e2e -- authentication.spec.ts accessibility.spec.ts
```

**Expected outcome**: all of the above pass with zero regressions and zero
new WCAG 2.1 AA violations (SC-002, SC-003).

## 4. Performance budget check (SC-004)

1. In Chrome DevTools → Performance (or Lighthouse), record a page load of
   `/` on a throttled "Fast 3G"/typical-broadband profile.
2. Confirm Largest Contentful Paint (the hero/CTA becoming visually complete
   and interactive) lands under 2.5 seconds.

## 5. Design-process artifacts to confirm exist (FR-010, SC-005, SC-006)

- `data-model.md`'s `Visual Direction` table lists 2-3 candidates, exactly
  one `selected`, with a `reviewedBy` of the product owner and
  `rejectionReason`s filled in for the rest.
- `contracts/visual-direction-review-contract.md`'s required-before-review
  checklist is satisfied for the selected direction.
- `contracts/content-inventory-contract.md`'s sign-off log has all 6
  categories resolved (not "pending").
- `contracts/i18n-key-migration-contract.md`'s migration mapping is filled
  in and the key-parity check (step 1 of its verification procedure) passes.
- A structured design review against Apple HIG principles (clarity,
  deference, depth) closes with zero unresolved high-priority findings
  (SC-005) — recorded wherever this feature's implementation tracks that
  (e.g. a design-audit note analogous to feature 028's `design-audit.md`, if
  produced).
