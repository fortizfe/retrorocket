# Quickstart: Validating the Retrospective Board Redesign

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This is a validation guide, not an implementation guide — it documents how
to run and manually/automatically verify the redesigned retrospective board
once implemented. See `data-model.md` and `contracts/` for what "correct"
means; see `tasks.md` (generated by `/speckit-tasks`) for how to build it.

## Prerequisites

- Repo dependencies installed: `cd retro-rocket && npm install`
- Firebase auth emulator running (board access requires sign-in):
  `npm run emulators` (separate terminal), or rely on `npm run e2e` which
  starts it automatically.
- The backend dev server running alongside the frontend for real
  realtime/REST responses: `npm run dev:all` (starts both `dev` and
  `dev:server`).
- At least two signed-in browser profiles/accounts, to exercise real-time
  multi-participant behavior (presence, typing, votes/reactions from
  another user, facilitator-only controls vs. a non-owner view).

## 1. Run the board locally

```sh
cd retro-rocket
npm run dev:all
```

Sign in, create or open a board, and navigate to `/retro/:id`.

**Check** (as a participant, using a second account/profile alongside the
owner where a capability is owner-only):

- Add, edit, and delete a card; content wraps, URLs stay clickable, line
  breaks are preserved (FR-002).
- Vote, like, and add/remove an emoji reaction on a card — the reaction
  picker opens already anchored to its trigger with no flash (FR-003).
- Drag a card to reorder it within a column and move it to another column
  (FR-004).
- Group two cards manually; run AI-suggested grouping and review a
  suggestion before accepting; collapse/expand and disband a group (FR-005).
- Toggle the action items column on; as the board owner, convert a card to
  an action item with an assignee and due date, and create/edit/delete an
  action item directly (FR-007).
- Open a second browser profile as another participant — confirm presence
  updates and typing indicators appear in real time while typing a card
  (FR-008).
- As the board owner, open the facilitator menu — start/pause/reset the
  countdown timer (visible to the other participant in real time), enable
  sentiment analysis, view the team mood dashboard, and write a private
  facilitator note (FR-009). As the non-owner participant, confirm the
  facilitator menu and the card's convert-to-action control are both
  absent.
- Open the export option, export to each of PDF/DOCX/TXT with visible
  progress and a success outcome; as the owner, confirm facilitator-only
  export options are available and absent for the non-owner (FR-010).
- Copy the board ID, copy/share the board link, and exit back to the
  dashboard (FR-011).

## 2. Verify accessibility and interaction requirements

1. **Keyboard/touch menu reachability (FR-012, SC-004)**: Tab to the
   options menu, facilitator menu, a card's menu, a column header menu, and
   the export popover using only the keyboard — confirm each receives
   visible focus, opens via Enter/Space, and dismisses via Escape, with no
   mouse involved. Separately, using a touch-emulated viewport (devtools
   device toolbar) or a real touch device, confirm every menu and card
   action is tappable without any prior hover/pointer-enter event.
2. **Reduced motion (FR-015)**: enable `prefers-reduced-motion: reduce` and
   repeat the primary flows (add/vote/react to a card, drag-and-drop, group,
   open every menu, export, start/pause the countdown) — confirm every one
   still completes and communicates success/failure without relying on
   animation.
3. **Responsive layout (FR-016)**: resize to a narrow mobile width — confirm
   columns stack (rather than forcing horizontal scroll of the whole board)
   and every menu/control remains reachable; resize to an ultra-wide desktop
   width — confirm the layout remains legible.

## 3. Performance/scale budget check (SC-001, SC-007)

1. Seed a column with 30+ cards (a small script/loop calling the card-create
   API, or an E2E fixture — author this seeding helper as part of
   implementation tasks if one doesn't already exist).
2. Add, vote, like, and react to cards — confirm each responds within
   ~100ms of the action.
3. Drag-and-drop a card within the seeded column — using Chrome DevTools'
   Performance panel (or the FPS meter in the Rendering tab), confirm the
   frame rate sustains at least 50fps with no dropped-frame stalls.
4. With up to 15 simulated/real concurrent participants active on the same
   board (E2E fixture or multiple browser profiles), confirm real-time
   updates (cards, votes, reactions, typing, presence) continue to render
   without perceptible lag.

## 4. Automated checks

```sh
cd retro-rocket

# Type-check and lint
npm run type-check
npm run lint

# Unit/component tests + coverage gate (branches 78 / functions 64 / lines 50 / statements 50)
npm run test:coverage

# Architecture boundary — the retrospective board MUST NOT import Firestore SDK directly
npx vitest run src/test/architecture/retrospective-board-no-firestore.test.ts --config vitest.config.ts

# If any new/changed design tokens were introduced, confirm WCAG contrast math still holds
npx vitest run src/test/lib/theme/contrast.tokens.test.ts --config vitest.config.ts

# E2E: retrospective board, creation/join, export, facilitator/countdown, concurrency, and accessibility
npm run e2e -- retrospective-board.spec.ts board-creation.spec.ts board-join.spec.ts export.spec.ts facilitator-countdown.spec.ts concurrent-board-session.spec.ts concurrent-board-network.spec.ts accessibility.spec.ts
```

**Expected outcome**: all of the above pass with zero regressions and zero
new WCAG 2.1 AA violations (SC-002, SC-003), including the new `/retro/:id`
coverage added to `accessibility.spec.ts` (`research.md` §6) — see
`contracts/functional-parity-contract.md` and
`contracts/accessibility-interaction-contract.md`.

## 5. Design-process artifacts to confirm exist (FR-018, SC-005, SC-006)

- `data-model.md`'s `Visual Direction` table lists 2-3 candidates, exactly
  one `selected`, with a `reviewedBy` of the product owner and
  `rejectionReason`s filled in for the rest.
- `contracts/visual-direction-review-contract.md`'s required-before-review
  checklist is satisfied for the selected direction.
- `contracts/functional-parity-contract.md`'s verification procedure has
  been run against both the baseline and the final implementation.
- `contracts/accessibility-interaction-contract.md`'s checklist is fully
  checked, not left partially unchecked.
- A structured design review against Apple HIG principles (clarity,
  deference, depth) closes with zero unresolved high-priority findings
  (SC-005) — recorded in `design-review.md` (analogous to feature 028's
  `design-audit.md` and features 029/031's `design-review.md`).
