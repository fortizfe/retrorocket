# Quickstart: Validating the Landing Page Redesign

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This is a validation guide, not an implementation guide — it documents how
to produce the Media Assets and how to run and manually/automatically verify
the redesigned landing page once implemented. See `data-model.md` and
`contracts/` for what "correct" means; see `tasks.md` (generated by
`/speckit-tasks`) for how to build it.

## Prerequisites

- Repo dependencies installed: `cd retro-rocket && npm install`
- Firebase emulators available (used both by E2E and by the media capture
  script): `npm run emulators` (separate terminal), or rely on
  `npm run e2e`, which starts them automatically.

## 1. Produce the Media Assets (FR-004, FR-005, FR-015)

Before the page can be visually reviewed with real content, the capture
script must have populated `public/landing-media/`:

```sh
cd retro-rocket
npm run emulators          # separate terminal, leave running
npx playwright test e2e/fixtures/landing-capture.ts --config playwright.config.ts
```

**Check** (`contracts/capture-script-contract.md`):
- The script exits successfully and `public/landing-media/{section}/{light,dark}.*`
  exists for every `Media Asset` entry in
  `src/features/landing/data/mediaAssets.ts`.
- Every video asset has a matching `light`/`dark` poster image.
- Spot-check a few files: seeded boards/cards show natural-language,
  realistic content (e.g. "Product Design Weekly" style names) — never
  `"Seed Board 0001"`/`"Seed card 0001"` placeholder strings, and never any
  real user's data (impossible by construction — the script only runs
  against the emulator, never a production project).

## 2. Run the page locally

```sh
cd retro-rocket
npm run dev
```

Open `http://localhost:5173/` (or the port Vite prints) unauthenticated.

**Check**:
- The first viewport (hero) shows one dominant, high-impact visual with
  minimal copy and a visible sign-in CTA, with no scrolling required, at a
  common desktop width (~1280-1440px), tablet width (~768-834px), and
  mobile width (~375-414px) — verify with browser devtools device toolbar
  (FR-001, SC-001).
- Scrolling below the hero moves continuously — nothing intercepts or locks
  the scroll gesture onto a section boundary (FR-002).
- Each section below the hero fills the viewport height and shows a real
  screenshot or video of the app, not an illustration/mockup (FR-004, US2
  Acceptance Scenario 1).
- Scroll slowly and observe parallax: movement is smooth, not abrupt; on a
  narrow/mobile viewport, parallax displacement is visibly reduced relative
  to desktop (FR-003, research.md #9).
- Any video section autoplays muted and loops while in view, and visibly
  pauses once scrolled out of view (FR-007, US2 Acceptance Scenario 4) —
  confirm via devtools' Elements panel or by watching CPU/network activity
  drop once the section leaves the viewport.
- Toggle the theme control — every section's screenshot/video swaps to the
  matching theme variant immediately, with no mismatched-theme asset ever
  visible (FR-006, US3, SC-006).
- Switch the browser/OS language between English and Spanish — all text
  renders correctly, no raw `landing.*` key strings visible, no layout
  breakage inside a full-screen section from differing text lengths
  (FR-009, Edge Cases).
- In devtools, enable "Emulate CSS prefers-reduced-motion: reduce" and
  reload — parallax is replaced by static positioning, video sections show
  their static poster frame instead of autoplaying, and all content remains
  fully readable/usable (FR-003, FR-007, US2 Acceptance Scenario 3).
- Throttle the network (devtools → Network → Slow 3G) and reload — the hero
  still becomes interactive quickly; sections further down lazy-load and
  fade in smoothly as you approach them, with no blank hold and no
  persistent skeleton/placeholder UI (FR-014).

## 3. Verify the sign-in flow still works end-to-end

With the Firebase auth emulator running:

1. Click "Sign in with Google" (or GitHub) — the existing OAuth flow
   completes exactly as before, as the sole conversion mechanism on the page
   (FR-008).
2. On first sign-in, the display-name setup step appears, styled using the
   new design system; saving a name proceeds to the dashboard.
3. Manually append `?auth_error=access_denied` to the landing URL and reload
   — confirm the corresponding error toast still surfaces, styled to match
   the new design (Edge Cases, FR-008).
4. While already signed in, navigate back to `/` — confirm the existing
   redirect-away-from-landing behavior still fires (Edge Cases, FR-008).

## 4. Automated checks

```sh
cd retro-rocket

# Type-check and lint
npm run type-check
npm run lint

# Unit/component tests + coverage gate, including the new Media Asset
# manifest contract test (contracts/media-asset-manifest-contract.md)
npm run test:coverage

# If any new/changed design tokens were introduced, confirm WCAG contrast math still holds
npx vitest run src/test/lib/theme/contrast.tokens.test.ts --config vitest.config.ts

# E2E: authentication + accessibility (WCAG 2.1 AA, both themes, keyboard tab order)
npm run e2e -- authentication.spec.ts accessibility.spec.ts
```

**Expected outcome**: all of the above pass with zero regressions and zero
new WCAG 2.1 AA violations (SC-002, SC-003).

## 5. Performance budget check (SC-004)

1. In Chrome DevTools → Performance (or Lighthouse), record a page load of
   `/` on a throttled "Fast 3G"/typical-broadband profile.
2. Confirm Largest Contentful Paint (the hero becoming visually complete and
   interactive) lands under 2.5 seconds — the below-the-fold Media Assets
   (screenshots/videos) must not be part of this critical path (FR-014).

## 6. Contracts and design-process artifacts to confirm satisfied

- `contracts/content-inventory-contract.md`'s sign-off log has all 5
  categories resolved (not "pending").
- `contracts/media-asset-manifest-contract.md`'s verification procedure
  passes (unit test + human review of `public/landing-media/`).
- `contracts/capture-script-contract.md`'s verification procedure passes,
  and `e2e/authentication.spec.ts`/`e2e/accessibility.spec.ts` are
  unaffected by the capture script's existence.

  deference, depth), using the constitution's mandated `apple-design`/
  `emil-design-eng`/`animate`/`review-animations` skills, closes with zero
  unresolved high-priority findings (SC-007).
- The product owner has reviewed the finished redesign against SC-008 (reads
  as professional/commercially credible, comparable to the Apple Vision Pro
  reference) with no requested reversion.
