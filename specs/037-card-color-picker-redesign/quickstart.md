# Quickstart: Validating the Card Color Picker Redesign

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This is a validation guide, not an implementation guide — it documents how
to run and manually/automatically verify the redesigned color picker
(including its new touch entry point, FR-011a, and the curated-catalog
remapping, FR-013a) once implemented. See `data-model.md` and `contracts/`
for what "correct" means; see `tasks.md` (generated by `/speckit-tasks`) for
how to build it.

## Prerequisites

- Repo dependencies installed: `cd retro-rocket && npm install`
- Firebase auth/firestore emulators running (board access requires
  sign-in): `npm run emulators` (separate terminal), or rely on `npm run
  e2e`, which starts them automatically.
- The backend dev server running alongside the frontend for real
  realtime/REST responses: `npm run dev:all` (starts both `dev` and
  `dev:server`).
- At least two signed-in browser profiles/accounts: one who owns a board
  and one who joins it as a non-owner participant (to verify edit-rights
  gating, FR-004).
- At least one existing board with several cards already carrying a spread
  of pre-curation colors, so the FR-013a remapping is genuinely observable,
  not just theoretical.

## 1. Run the board locally

```sh
cd retro-rocket
npm run dev:all
```

Sign in as the board owner, create (or open) a board with existing colored
cards, and navigate to `/retro/:id`; sign in as a second account in another
profile/browser and join the same board.

**Check, at a desktop viewport width:**

- As a participant with edit rights on a card, open its color picker —
  confirm the currently applied color is unambiguously marked (FR-005),
  browse the curated catalog, and select a different color; confirm the
  card updates immediately and the change appears in real time for the
  other participant (FR-002).
- Confirm each color's name is visible/available (hover, focus, or
  long-press) to distinguish visually similar colors (FR-006).
- Press Escape (or click outside) while the picker is open — confirm it
  closes without changing the card's color (FR-007).
- As the non-owner/non-edit participant, confirm no color picker trigger is
  offered on a card they cannot edit (FR-004).
- Open the add-card form in a column, open its color picker, select a
  non-default color, and submit — confirm the new card is created with
  that color (User Story 3).

**Check, at a touch/narrow viewport width (FR-011a — new capability):**

- Without performing any hover gesture, locate and open a card's color
  picker via the new touch-reachable entry point; select a color and
  confirm the same outcome as the desktop flow above.
- Repeat from the add-card form.
- Confirm the drag handle and any other nearby card control remain
  reachable and are not visually crowded out by the new touch affordance.

**Check catalog curation and remapping (FR-013, FR-013a):**

- On a board with cards using colors that were curated away by the
  selected direction, confirm every such card now renders a valid,
  recognizable color (its `Color Catalog Curation Mapping` equivalent from
  `data-model.md`) — no card shows a broken or blank swatch.
- Open the picker on a freshly-remapped card and confirm the panel marks
  its (remapped) current color, not a stale or missing selection.

## 2. Verify accessibility and interaction requirements

1. **Keyboard/touch reachability (FR-007, FR-011a, SC-003, SC-004)**: Tab to
   a card's color-picker trigger using only the keyboard, at both a
   desktop and a touch/narrow viewport — confirm it receives visible
   focus, opens via Enter/Space, navigates among swatches via arrow keys
   (or the selected direction's equivalent), and dismisses via Escape,
   with no mouse involved. Separately, using a touch-emulated viewport
   (devtools device toolbar) or a real touch device, confirm the trigger is
   visible without any prior hover/pointer-enter event, and that opening
   the panel and selecting a color both work via tap alone.
2. **Reduced motion (FR-010)**: enable `prefers-reduced-motion: reduce` and
   repeat: open/close the picker and select a color — confirm it still
   completes and communicates its result without relying on animation.
3. **Locale (FR-008, User Story 5)**: switch between English and Spanish —
   confirm every color's name, tooltip, and aria-label renders in the
   active locale (a real change from today's hardcoded-Spanish behavior,
   `research.md` §4), and that differing text lengths don't break the
   panel's layout.
4. **Responsive layout (FR-011)**: resize across mobile and desktop widths —
   confirm the picker is reachable and legible at every size, on both the
   existing card and the add-card form.

## 3. Automated checks

```sh
cd retro-rocket

# Type-check and lint
npm run type-check
npm run lint

# Unit/component tests + coverage gate
npm run test:coverage

# Architecture boundary — no direct Firestore access from these components
npx vitest run src/test/architecture/retrospective-board-no-firestore.test.ts --config vitest.config.ts

# Catalog + accessibility-contrast suites (feature 009's per-swatch WCAG assertions, extended for the curated set)
npx vitest run src/test/lib/utils/cardColors.test.ts src/test/lib/utils/cardColors.a11y.test.ts --config vitest.config.ts

# Color picker component suites
npx vitest run src/test/lib/components/ui/ColorPicker.test.tsx src/test/lib/components/ui/ColorPickerClean.test.tsx --config vitest.config.ts

# If any new/changed design tokens were introduced, confirm WCAG contrast math still holds
npx vitest run src/test/lib/theme/contrast.tokens.test.ts --config vitest.config.ts

# E2E: the board itself (includes the color-selection scenario) and accessibility
# (including the new touch-viewport coverage)
npm run e2e -- retrospective-board.spec.ts accessibility.spec.ts
```

**Expected outcome**: all of the above pass with zero regressions and zero
new WCAG 2.1 AA violations (SC-002, SC-003), including new touch-viewport
coverage added to `accessibility.spec.ts` and the new FR-013a remapping
migration test — see `contracts/functional-parity-contract.md` and
`contracts/accessibility-interaction-contract.md`.

## 4. Design-process artifacts to confirm exist (FR-014, SC-005, SC-006)

- `data-model.md`'s `Visual Direction` table lists 2-3 candidates, exactly
  one `selected`, each with its own committed `touchTriggerPresentation`
  and `curatedCatalog`, reviewed by the product owner with
  `rejectionReason`s filled in for the rest.
- `contracts/visual-direction-review-contract.md`'s required-before-review
  checklist is satisfied for the selected direction, including its
  proposed `Color Catalog Curation Mapping` entries.
- `contracts/functional-parity-contract.md`'s verification procedure has
  been run against both the baseline and the final implementation.
- `contracts/accessibility-interaction-contract.md`'s checklist is fully
  checked, not left partially unchecked.
- A structured design review against Apple HIG principles (clarity,
  deference, depth) closes with zero unresolved high-priority findings
  (SC-005) — recorded in `design-review.md` (analogous to features
  028/029/031/033/036's own design-review documents).
