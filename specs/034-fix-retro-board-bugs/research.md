# Phase 0 Research: Retro Board Bug Fixes

All four defects were investigated directly against the current codebase (branch `main`, commit `6455fcd`). No `NEEDS CLARIFICATION` markers remain in the Technical Context — every unknown below was resolved by reading the actual implementation rather than by assumption.

## 1. Menu anchoring (User Story 1 / FR-001–004)

**Decision**: Split each affected menu's floating panel into two nested elements — an outer, non-animated element that receives Floating UI's `ref={refs.setFloating}` and `style={floatingStyles}` (positioning only), and an inner `motion.div` that owns the `initial`/`animate`/`exit` entrance/exit animation (opacity/y/scale). Apply this to `RetrospectiveTopbar.tsx`'s options-menu panel and `FacilitatorMenu.tsx`'s panel.

**Rationale**: Both panels currently apply `style={floatingStyles}` **and** Framer Motion's `initial`/`animate`/`exit` (which includes `y` and/or `scale`) to the *same* `motion.div` (`RetrospectiveTopbar.tsx` lines ~120–130; `FacilitatorMenu.tsx` lines ~180–188). Floating UI's `floatingStyles` encodes the computed anchor position as `position: fixed; top: 0; left: 0; transform: translate(Xpx, Ypx)`. Framer Motion, animating `y`/`scale` on that same node, writes its own `transform` value (e.g. `translateY(-6px) scale(0.98)`) on every animation frame, which overwrites — not composes with — the positioning `transform` Floating UI computed. With no active positioning transform, the panel renders at its base `top: 0; left: 0`, i.e. pinned to the viewport's top-left corner — exactly the reported symptom, and it explains why the bug survived the commit that introduced `useBoardMenuOverlay`/Floating UI in the first place (`936e894`): the hook's positioning math is correct, but its output is being clobbered downstream by an unrelated animation prop on the same DOM node.

Confirmation this is the actual mechanism, not a guess: `ReactionPicker.tsx` (`src/features/boards/retrospective/components/ReactionPicker.tsx`), which the codebase already cites as this hook's original reference implementation (`useEmojiPicker`), applies `style={floatingStyles}` to a **plain `<div>`** with no competing `animate` prop — and it positions correctly. It is the only floating-panel consumer in the codebase that avoids the collision, which is consistent with the diagnosis.

**Alternatives considered**:
- *Use Floating UI's `transform: false` option and switch to `top`/`left` pixel values instead of a CSS transform.* Rejected: still collides, because Framer Motion would then need `x`/`y` motion values expressed as *additional* offsets on top of literal `top`/`left`, and Framer Motion's `style` merging still ends up writing a `transform` for `scale`, recreating the same class of conflict for any menu that also scales in mid-open (facilitator menu does).
- *Drop the entrance/exit animation on these two menus entirely.* Rejected: regresses the polish already delivered in the `936e894` redesign and violates Constitution Principle IX's expectation that motion decisions go through the `animate` skill, not be removed reactively.
- *Fix only via CSS `will-change`/`contain` tricks on ancestors.* Rejected: doesn't address the root cause (both libraries targeting the same `transform` property on the same node) and Floating UI's own docs recommend the split-node pattern for exactly this combination.

**Scope note**: `CardMenu.tsx` and `ColumnHeaderMenu.tsx` share the identical pattern (`motion.div` + `style={floatingStyles}` + `animate` including `scale`) and are very likely affected the same way, but neither is named in spec.md's User Story 1 or in the user's bug report. Left untouched per Constitution Principle V (Simplicity/YAGNI) — see plan.md Complexity Tracking.

## 2. Column header layout (User Story 2 / FR-005–008)

**Decision**: Restructure `GroupableColumn.tsx`'s header block (currently a single flex row, lines ~224–272) into three stacked rows: row 1 = icon + title + card-count badge + optional "N groups" badge (the title-adjacent, non-interactive content); row 2 = `column.description`, rendered only when present; row 3 = `ColumnHeaderMenu` (group control) + the "Add" `Button`, right-aligned.

**Rationale**: The current single-row layout (`flex items-center justify-between gap-2`) gives every element `shrink-0` except the title's wrapper, so the title — the one piece of information the row exists to convey — is the only thing that shrinks under space pressure, which is exactly backwards. Moving the two interactive controls to their own row removes them from competition with the title entirely, matching the exact row assignment requested (title+count / subtitle / group+add).

**Alternatives considered**:
- *Keep one row but truncate less aggressively (e.g. `min-width` on the title).* Rejected: doesn't scale to narrow viewports or long titles, and the user explicitly asked for a specific three-row structure, not a truncation tweak.
- *Move only the Add button to its own row, keep group button with the title.* Rejected: the user's own description groups "el botón de agrupar y el de añadir" together on the third row; a partial move doesn't match the request and leaves the same crowding for one of the two controls.

## 3. Duplicate private-note content on save (User Story 3 / FR-009–010)

**Decision**: When a note is saved successfully (not cancelled), the create-note `motion.div` (`NotesTab.tsx` lines ~176–221) must not be allowed to keep displaying its last-rendered (pre-save) content for the duration of an `AnimatePresence` exit transition. Concretely: branch the exit behavior so a successful save collapses/removes the form without replaying its default exit animation (or clears the frozen exit-snapshot's visible text before it can render), while a user-initiated Cancel keeps the existing exit animation. This is a motion-timing decision and MUST be made via the `animate` skill per Constitution Principle IX, not implemented ad hoc.

**Rationale**: `handleCreateNote` (lines ~60–75) already reorders `setIsCreating(false)` and `setNewNoteContent('')` to occur *before* `await createNote(content)`, specifically to prevent the textarea and the realtime-delivered note from being mounted together — but that fix only addresses React state ordering. `AnimatePresence` does not react to further state changes on an element already scheduled for removal: once `{isCreating && (...)}` evaluates false, `AnimatePresence` captures the *last rendered instance* of that `motion.div` (still showing the pre-save content, since that was the render immediately before the state flip took effect) and keeps it mounted, unchanged, for the length of its exit transition (`exit={{opacity:0,height:0,y:-20}}`, no explicit `transition`, so it uses Framer Motion's default duration). If the realtime channel delivers the newly created note and renders its read-only `<p>{note.content}</p>` (lines ~272–277) before that exit transition finishes, both elements are simultaneously in the DOM with identical text — precisely the two-element strict-mode violation Playwright reported at `e2e/retrospective-board.spec.ts:1102`.

**Alternatives considered**:
- *Increase the Playwright assertion's specificity (scope `getByText` to `p` only) without touching the component.* Rejected: this masks a real, user-visible flicker (confirmed by the constitution's TDD principle requiring the underlying behavior — not just the test — to be correct); the spec's Assumptions section explicitly frames this as a product-behavior fix, not a test-only patch.
- *Remove the exit animation on the create-note form entirely.* Rejected: same reasoning as menu removal above — an unjustified motion regression when a scoped fix (skip/shorten the animation specifically on the save path) is available.

## 4. Typing indicator not clearing / duplicating across columns (User Story 4 / FR-011–013)

**Decision (part A — failed writes)**: Keep the existing per-column serialized-write design in `OptimizedTypingStatusService` (per-key promise chaining) and `useTypingStatus`'s per-column 3-second inactivity timer, but close the gap the spec's Edge Cases and FR-013 call out: a failed `isActive:false` write was previously discarded with no retry (`OptimizedTypingStatusService.ts`, pre-fix lines ~18–20), relying solely on the server's disconnect-safety TTL sweep as a fallback. Added a bounded, off-chain retry (2 attempts, 500ms apart) specifically for failed `isActive:false` writes, so a clear-write's failure alone can't leave a stale indicator.

**Decision (part B — the actual mechanism behind the reported E2E failure, found via live instrumentation)**: Part A, while a real and independently worth-having improvement, turned out **not** to be the cause of the specific "two elements visible" failure reproduced from the bug report. Direct network/WebSocket/console instrumentation of a live failing run (Playwright `page.on('request'/'response'/'websocket'/'console')`, temporarily added and removed) showed: **every** typing-status write succeeded (204 responses throughout), and the client's `applyTypingStatusChange` reducer (`useRetrospectiveRealtimeSync.ts`) correctly converged to the right state after every single event — verified by temporarily logging its `before`/`after` id lists, which never showed the two "typing" columns coexisting in `typingStatuses`. The actual bug is in the **rendering layer**: `TypingPreview.tsx`'s visible card is wrapped in `AnimatePresence`, gated directly on `typingUsers.length > 0`. When a column's typist count drops to zero, `AnimatePresence` freezes the *last-rendered* card — including its baked-in `formatTypingText()` string, e.g. "X está escribiendo" — for the length of its exit transition (a spring, `stiffness:500, damping:30, mass:0.8`, several hundred ms to settle). If a *different* column's indicator is genuinely active (or becomes active) during that same window, both cards are simultaneously on screen with visually/textually-identical "... está escribiendo" content, matching Playwright's global (not per-column-scoped) `span.text-blue-700` locator — the exact same defect class as User Story 3's note-duplication bug (`AnimatePresence` freezing stale content past a state transition), just in a different component. Fixed with the identical technique used for `NotesTab.tsx`: `TypingPreview` now stages `displayedUsers`/`isPresent` local state, clearing `displayedUsers` via `flushSync` in its own commit *before* `isPresent` flips (in a following commit) to close `AnimatePresence`'s gate — so the frozen exit snapshot's content is always empty, never a departing typist's name, regardless of animation duration or how fast another column's indicator appears. The always-mounted accessible live region continues to read directly from the live `typingUsers` prop (not the frozen `displayedUsers`), so screen-reader announcements are unaffected and remain immediate.

**Rationale**: `useTypingStatus.ts`'s `INACTIVITY_TIMEOUT_MS` (3000ms) already fires `stopTyping(column)` per column independently and correctly (confirmed by reading lines 41–42, 113–116, 133–136) — the *decision* to stop, and the write clearing it, were never the bug in this specific failure. This is a valuable lesson in this feature's own execution: the original hypothesis (a discarded failed write) was plausible, well-reasoned from static code reading, and worth fixing regardless — but it was not the actual root cause of the reported E2E failure, which only surfaced under live, instrumented reproduction. A belt-and-suspenders client-side staleness filter (an intermediate hypothesis — discard `typingStatuses` entries older than a max age) was also tried and discarded once instrumentation showed the *data* was never stale; only the *rendered* content was.

**Alternatives considered**:
- *Shorten `INACTIVITY_TIMEOUT_MS`.* Rejected: doesn't address a failed write or the animation-freeze issue; a shorter timeout still risks reintroducing the flicker-while-still-typing regression feature 026 was written to fix.
- *Retry indefinitely until success (part A).* Rejected: unbounded retries against a possibly-offline client contradict the "bounded time" requirement (FR-011/SC-004); a capped retry bounds the worst case instead.
- *Client-side staleness filter on `typingStatuses` by age (intermediate hypothesis).* Rejected once instrumentation proved the state was never stale — the filter would have been unjustified complexity solving a problem that didn't exist (Constitution Principle V).
- *Remove `TypingPreview`'s exit animation entirely.* Rejected: same reasoning as US1/US3 — regresses delivered polish and violates Constitution Principle IX's expectation that motion decisions go through the `animate` skill deliberately, not be stripped reactively, when a scoped, deterministic fix (staged local state + `flushSync`) is available.
- *Move indicator clearing fully server-side (e.g., shorten the TTL sweep interval).* Rejected: out of scope — this feature is frontend-only per Technical Context/Storage above, and the TTL sweep is an existing server-side safety net, not the primary clearing mechanism; changing backend sweep cadence is a larger, unrequested change. It also wouldn't have fixed the actual (rendering-layer) bug.
