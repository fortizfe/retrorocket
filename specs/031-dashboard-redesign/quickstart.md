# Quickstart: Validating the Mis Tableros (Dashboard) Redesign

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This is a validation guide, not an implementation guide — it documents how
to run and manually/automatically verify the redesigned dashboard once
implemented. See `data-model.md` and `contracts/` for what "correct" means;
see `tasks.md` (generated by `/speckit-tasks`) for how to build it.

## Prerequisites

- Repo dependencies installed: `cd retro-rocket && npm install`
- Firebase auth emulator running (dashboard access requires sign-in):
  `npm run emulators` (separate terminal), or rely on `npm run e2e` which
  starts it automatically.
- The backend dev server running alongside the frontend for real
  `/api/boards*` responses: `npm run dev:all` (starts both `dev` and
  `dev:server`).

## 1. Run the dashboard locally

```sh
cd retro-rocket
npm run dev:all
```

Sign in and navigate to `/dashboard` (or `/mis-tableros`).

**Check**:
- All boards you created and joined are listed, with title, description,
  creation date (in your active language), participant count, and a clear
  creator/joined indicator (FR-002, FR-003).
- Search narrows the list by title/description; clearing it restores the
  full list (FR-009).
- Filtering by All / Created / Joined shows the correct live count per
  option (FR-010).
- Sorting by name and by date toggles direction on repeat selection
  (FR-011).
- Create a board from a template, confirm you land inside it and it now
  appears in the list (FR-004).
- Join a board by ID (use a second account/browser profile to create one to
  join), confirm you land inside it and it appears in the list (FR-005).
- As the owner, rename a board and reload — the new title persists (FR-007).
- As the owner, delete a board through its confirmation step — it
  disappears from the list; as a non-owner on a joined board, confirm no
  rename/delete control is offered at all (FR-008, US3 Acceptance
  Scenario 3).
- Give a board a very long title/description — confirm it truncates
  gracefully without breaking the layout, and that the full text is
  available on demand (e.g. hovering/focusing reveals a native tooltip).

## 2. Verify the two corrected defects and the reachability requirement

1. **Reachability at scale (FR-012, SC-001)**: seed 200+ boards for a test
   account (e.g. a small script/loop calling the create-board API, or an
   E2E fixture — author this seeding helper as part of implementation
   tasks if one doesn't already exist). Confirm every board is reachable in
   every layout the shipped direction offers — none become inaccessible
   because of pagination, scroll, or layout constraints.
2. **Keyboard/touch action reachability (FR-015, SC-004)**: Tab to an owned
   board's rename/delete controls using only the keyboard — confirm they
   receive visible focus and activate via Enter/Space, with no mouse
   involved. Separately, using a touch-emulated viewport (devtools device
   toolbar) or a real touch device, confirm the same controls are tappable
   without any prior hover/pointer-enter event.
3. **Date localization (FR-016, SC-005)**: switch the active language
   between English and Spanish (in-app language selector) — confirm every
   board's displayed creation date re-renders in that language, not always
   in Spanish.

## 3. Performance budget check (SC-001)

With the 200+ board list from step 2:

1. Type into the search field — confirm the list narrows with no
   perceptible lag (target: under 300ms from keystroke to updated list).
2. Change the sort key/direction and the scope filter — same target.
3. Scroll through the full list — using Chrome DevTools' Performance panel
   (or the FPS meter in the Rendering tab), confirm the frame rate sustains
   at least 50fps with no dropped-frame stalls, in whichever layout(s) the
   shipped direction offers.

## 4. Automated checks

```sh
cd retro-rocket

# Type-check and lint
npm run type-check
npm run lint

# Unit/component tests + coverage gate (branches 78 / functions 64 / lines 50 / statements 50)
npm run test:coverage

# Architecture boundary — dashboard/create-board MUST NOT import Firestore SDK
npx vitest run src/test/architecture/dashboard-no-firestore.test.ts --config vitest.config.ts

# If any new/changed design tokens were introduced, confirm WCAG contrast math still holds
npx vitest run src/test/lib/theme/contrast.tokens.test.ts --config vitest.config.ts

# E2E: dashboard, board creation/join, and accessibility (WCAG 2.1 AA, both themes, all states)
npm run e2e -- dashboard-list.spec.ts dashboard-manage.spec.ts board-creation.spec.ts board-join.spec.ts accessibility.spec.ts
```

**Expected outcome**: all of the above pass with zero regressions and zero
new WCAG 2.1 AA violations (SC-002, SC-003), and the extended/new specs
(`BoardRow.test.tsx` for keyboard/touch reachability, `dashboard-locale.spec.ts`
for locale-aware dates) pass against the corrected behavior — see
`contracts/functional-parity-contract.md`.
