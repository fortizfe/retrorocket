# Phase 0 Research: Fix Typing Indicator Flicker

No items in Technical Context were left as `NEEDS CLARIFICATION` — the spec's `/speckit-clarify` session already resolved the two scope-impacting decisions (the 3-second grace period; accessibility in scope via a live-region announcement). What follows is the code-level investigation that turns those decisions into a concrete plan.

## 1. Root cause of "shows and hides an instant later" (FR-002, User Story 1)

**Decision**: The defect is a conflict between two independently-reasonable, uncoordinated timers, both already present in the code before this feature:

- `useTypingStatus.startTyping` (`src/features/boards/retrospective/hooks/useTypingStatus.ts:60-91`) throttles repeat calls into the write layer to once per `UPDATE_THROTTLE = 2000ms` per column — a keystroke-spam guard.
- `OptimizedTypingStatusService.setTypingStatusDebounced` (`src/features/boards/retrospective/services/OptimizedTypingStatusService.ts:21-58`), on every `isActive:true` call, unconditionally schedules a `DEBOUNCE_DELAY = 300ms` timer (`cleanupTimer`) that writes `isActive:false` unless *another* `isActive:true` call arrives within that same 300ms to reset it.

Because the hook throttles refresh calls to once per 2000ms, the 300ms reset essentially never lands in time. The observed write sequence while a user types continuously is: `true` at t=0, `false` at t≈300ms (service's own auto-off), silence until t=2000ms (hook's next throttled refresh), `true` again, `false` again at t≈2300ms, repeating. Every throttle window produces one on/off flicker — exactly "se muestra y al instante siguiente se oculta."

**Evidence, not just hypothesis**: `OptimizedTypingStatusService.test.ts:26-32`'s existing test is literally named `'auto-deactivates after the 300ms debounce window if no further keystroke resets it'` and asserts `mockSetTypingStatus` is called with `false` 300ms after a `true` call with no further input — this test documents the bug as if it were the intended design. `useTypingStatus.test.ts:153-165` separately confirms the hook only forwards one call per burst of rapid `startTyping` invocations ("should throttle rapid typing updates"), i.e., confirms the 2000ms throttle is real and active. Neither test file's author appears to have reasoned about the other file's timer — the 300ms window and the 2000ms window were never designed against each other.

**Why manual testing shows a real, if brief, flash**: the service's very first `isActive:true` call (`!this.debounceTimers.has(key + '_initialized')` branch) writes immediately, so the indicator does appear on the first keystroke; the 300ms auto-off is scheduled in the same call, so it reliably disappears well under a second later, before the hook's next throttled refresh at t=2000ms restores it. This matches the reported "se muestra y al instante siguiente se oculta" precisely, including that it is not a one-time glitch but repeats for as long as the user keeps typing.

**Alternatives considered**:
- *Increase `DEBOUNCE_DELAY` past `UPDATE_THROTTLE`* (e.g. 300ms → 2500ms) — would mask the symptom without fixing the underlying design problem (two independent owners of the same decision) and would leave a service-level "guess when typing stopped" mechanism duplicating what the hook already does, an SRP violation the next change to either constant could silently reintroduce.
- *Decrease `UPDATE_THROTTLE` below `DEBOUNCE_DELAY`* (e.g. 2000ms → 250ms) — would eliminate the visible flicker but reintroduce near-every-keystroke backend writes, defeating the throttle's original purpose and increasing load for no behavioral benefit.

## 2. Fix design: single owner for "has this user stopped typing" (FR-002, FR-003)

**Decision**: `OptimizedTypingStatusService.setTypingStatusDebounced` is reduced to an unconditional, immediate pass-through: `isActive:true` calls `backendRetrospectiveClient.setTypingStatus(retrospectiveId, column, true)` directly; `isActive:false` continues to do the same with `false`, exactly as today. No timer, no `activeStatuses`/`debounceTimers`/`_initialized` bookkeeping is needed once the auto-deactivation responsibility is removed — `cleanupUserTypingStatus` keeps its existing per-column explicit-deactivation behavior (unchanged; it does not depend on the removed timer logic).

`useTypingStatus`'s existing local "assume stopped" timer (`useTypingStatus.ts:84-88`, currently `4000ms`) becomes **3000ms**, matching the Clarification session's answer, and keeps its existing behavior: it is (re)scheduled inside `startTyping` on every call and reset via `clearTimeout`/reschedule, so it always reflects "3 seconds since the most recent keystroke," and it fires the hook's own `stopTyping()`, which performs an immediate, explicit `isActive:false` write — unchanged from today.

**Rationale**: This directly satisfies Clarification Q1 (3-second grace period) and FR-002/FR-003. The hook already has everything needed to own this decision correctly — per-column recency tracking (`lastUpdateTimers`), an explicit stop path wired to submit/cancel/blur/empty-input/unmount (`GroupableColumn.tsx:114-163`, `useTypingStatus.ts:41-57`) — the service layer's independent timer was redundant *and* the actual source of the conflict. Removing it is a strict simplification (Constitution V), not a substitution of one timer for another.

**Alternatives considered**:
- *Have the service query the hook (or vice versa) to coordinate two timers* — rejected: adds cross-module coupling and complexity to preserve two mechanisms doing the same job; Constitution IV (SOLID/SRP) is better served by one owner.
- *Move the write-throttling (`UPDATE_THROTTLE`) into the service instead of the hook* — rejected: the hook already needs per-column recency state for its own inactivity timer, so co-locating both there avoids splitting related state across two files; also a larger diff than necessary for this fix.

## 3. Disconnect / connection-loss bound (FR-004, User Story 2 AS3)

**Decision**: Retune `FirestoreRealtimeGatewayAdapter.ts`'s existing safety-net sweep — `TYPING_STATUS_TTL_MS` from `5000` to `3000`, `TYPING_STATUS_SWEEP_INTERVAL_MS` from `1000` to `500` — giving a worst-case bound of last-write-age 3000ms + up to one sweep tick (500ms) ≈ 3.5s, consistent with the ±0.5s tolerance already established for SC-002's inactivity case. No other change to this adapter.

**Rationale**: For a *connected* user who stops typing (User Story 2 AS1), the client's own 3-second inactivity timer (§2) already performs an immediate, explicit delete — the server sweep is never the critical path there. For an *actually disconnected* user (tab closed, network lost, crash), no client-side code can run, so the server-side sweep is the only mechanism that can ever clear the indicator for other viewers, and it must independently meet the same ~3-second bound (FR-004). Since the two safety margins that motivated the original 5000ms/1000ms values (client refresh cadence `UPDATE_THROTTLE = 2000ms`, and general safety headroom) still hold at 3000ms/500ms — 2000ms refresh vs 3000ms TTL leaves a 1000ms margin, same ratio-of-headroom class as before — tightening these two constants is sufficient and requires no new mechanism.

**Alternatives considered**:
- *Proactive cleanup on WebSocket close* (`ws.on('close', ...)` in `realtimeUpgrade.ts:112`, which already has `uid` and `retrospectiveId` in scope) actively deleting that user's `typingStatus` docs — would give a near-instant bound for *graceful* disconnects (tab close, navigation) specifically, strictly better than a sweep-based bound for that subset of cases. Rejected for this feature per Constitution V (Simplicity/YAGNI): it requires threading a new `TypingStatusPort`-shaped dependency into the WS upgrade layer (today it only depends on `RealtimeGatewayPort`, deliberately kept Firestore-agnostic per that port's own docstring) purely to shave the already-compliant ~3.5s sweep bound down further for a subset of disconnect cases, while abrupt disconnects (crash, network black hole) still fall back to the same sweep regardless — so the sweep-tightening alone already meets FR-004 for *all* disconnect cases uniformly, and the proactive path would only reduce latency further for a case that's already within bound. Left as a documented option, not adopted.
- *Leave the TTL at 5000ms and rely only on the client's inactivity timer* — rejected: does not cover disconnects, where no client code runs; FR-004 would remain unmet in exactly the scenario it targets.

## 4. Accessibility: perceiving typing status without sight (FR-009, SC-006, User Story 4)

**Decision**: Add a permanently-mounted element inside `TypingPreview.tsx` — visually hidden (existing `sr-only`-equivalent utility already used elsewhere in this codebase's Tailwind setup), `role="status"`, `aria-live="polite"`, `aria-atomic="true"` — whose text content is the same string the visible card already computes via `formatTypingText()` (empty string when `typingUsers.length === 0`). This element is rendered unconditionally (outside the `AnimatePresence`/`typingUsers.length === 0` early-return branch that controls the *visual* card), so it exists in the DOM before the first typing event ever occurs.

**Rationale**: Screen readers only reliably announce changes to a live region that was already present in the accessibility tree *before* the content change — a region that is mounted and populated in the same render (as the current `typingUsers.length === 0 ? null : ...` structure would produce for the visual card) is a well-documented reliability gap across screen reader/browser combinations. Reusing `formatTypingText()`'s existing output means no new user-facing string is introduced anywhere in the codebase, so this change satisfies the letter of the i18n Additional Standard ("every new feature that introduces user-visible text must add keys") without requiring i18n migration of the pre-existing hardcoded Spanish text — that migration is unrelated, pre-existing debt outside this bug fix's scope. `aria-atomic="true"` ensures the entire updated phrase (e.g., "Ana y 2 más están escribiendo") is announced as one unit rather than a diff, avoiding the confusing partial-word announcements `aria-atomic="false"` can produce. No re-announcement occurs when the underlying text is unchanged, because React only updates the DOM (and triggers the live-region observer) when the computed string actually differs — satisfying FR-009's "MUST NOT re-announce while the state is unchanged" without any extra bookkeeping.

**Alternatives considered**:
- *`aria-live` on the existing `motion.div` that already mounts/unmounts* — rejected per the reliability concern above: a region that doesn't exist in the DOM until the first typing event is exactly the unreliable pattern being avoided.
- *A `role="alert"` (assertive) region* — rejected: typing status is informational, not urgent/interrupting; `polite` is the correct WCAG 4.1.3 category for this kind of status update, and matches how similar "someone is doing X" indicators are conventionally implemented.
- *New dedicated i18n keys for a screen-reader-specific phrasing* — rejected as unnecessary scope expansion (Constitution V): the existing visible phrasing is already a complete, correct sentence: reusing it is simpler and keeps the visual and accessible experience in sync by construction.

## 5. Regression surface

**Decision**: No change to the `POST /api/retrospectives/:id/typing` route, `SetTypingStatus` use case, `TypingStatusPort`/`FirestoreTypingStatusAdapter` (doc shape, doc id pattern, `isActive:false` → delete semantics), the WS `typingStatus` `entity_change` event shape, or `useRetrospectiveRealtimeSync`'s `applyTypingStatusChange` reducer. The fix is confined to (a) removing a redundant/conflicting client-side timer, (b) one constant change in the hook's local inactivity timeout, (c) two constant changes in the server's safety-net sweep, and (d) an additive, non-visual accessibility element. Every existing consumer of the `typingStatuses` slice (`TypingProvider`, `GroupableColumn`, `TypingPreview`) keeps its current props/shape.

**Rationale**: Confirms the "no wire-protocol change" claim in plan.md's Technical Context — this is a client-timing-ownership fix plus two server constant tunings plus one additive accessibility element, consistent with Constitution V.
