# Quickstart: Validating the Export Window Redesign

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This is a validation guide, not an implementation guide — it documents how
to run and manually/automatically verify the redesigned export window
(desktop-anchored panel, mobile bottom sheet, and the background-export/
toast behavior) once implemented. See `data-model.md` and `contracts/` for
what "correct" means; see `tasks.md` (generated by `/speckit-tasks`) for how
to build it.

## Prerequisites

- Repo dependencies installed: `cd retro-rocket && npm install`
- Firebase auth emulator running (board access requires sign-in):
  `npm run emulators` (separate terminal), or rely on `npm run e2e` which
  starts it automatically.
- The backend dev server running alongside the frontend for real
  realtime/REST responses: `npm run dev:all` (starts both `dev` and
  `dev:server`).
- At least two signed-in browser profiles/accounts: one who owns a board
  (facilitator) and one who joins it as a non-owner participant, plus a
  board with a handful of cards, at least one facilitator note, and
  sentiment analysis enabled, so the always-included-content notice and the
  facilitator-only zone are meaningfully exercised.

## 1. Run the board locally

```sh
cd retro-rocket
npm run dev:all
```

Sign in as the board owner, create a board, and navigate to `/retro/:id`.

**Check, at a desktop viewport width:**

- Open the options menu and select "Export" — confirm the options panel
  closes immediately and the export panel opens anchored to the same
  "Options" trigger button (not a screen-centered dialog) (FR-002).
- Select each format (PDF, TXT, DOCX), edit the custom title, toggle the
  logo/statistics/action-items options, and — as the owner — toggle a
  facilitator-only option; confirm each change is reflected immediately
  (FR-004).
- Start an export; confirm progress, then success, feedback renders clearly
  in the panel, and the panel auto-closes on success (FR-007).
- Start another export, then press Escape (or click outside the panel)
  while it's still in progress: confirm the panel closes but the export
  keeps running, and a toast notification surfaces its outcome once it
  finishes (FR-007a).
- Reopen the export panel while a background export from the step above is
  still running (if timing allows): confirm it reflects that job's current
  in-progress state rather than starting a duplicate export.

**Check, at a mobile viewport width:**

- Open the options menu's mobile entry point and select "Export" — confirm
  the export window opens as a bottom sheet sliding up from the screen edge
  (FR-003), not the desktop-style anchored panel.
- Repeat the format selection, option toggles, and export start/dismiss/
  toast flow above, entirely by touch (FR-003, FR-007a).

**Check, as a non-owner participant:**

- Open the export window (either viewport) and confirm the facilitator-only
  zone is entirely absent, not merely disabled (FR-006).

## 2. Verify accessibility and interaction requirements

1. **Keyboard/touch reachability (FR-008, SC-003)**: Tab to the options
   menu trigger, open it, and Tab to "Export" — confirm Enter opens the
   export panel anchored correctly, every control inside it (format grid,
   title input, toggles, export/cancel buttons) is keyboard-reachable, and
   Escape dismisses it. Separately, using a touch-emulated viewport
   (devtools device toolbar) or a real touch device, confirm the same for
   the mobile sheet, with no control depending on a prior hover/
   pointer-enter event.
2. **Dismiss-during-export (FR-007a)**: start an export, dismiss the window,
   and confirm the export still completes and its outcome is surfaced via
   toast, exactly once, with no duplicate in-panel banner rendering
   afterward.
3. **Reduced motion (FR-011)**: enable `prefers-reduced-motion: reduce` and
   repeat: open/close the export window in both presentations, and move
   through idle → exporting → success/error — confirm every one still
   completes and communicates its result without relying on animation.
4. **Responsive layout**: resize across mobile, tablet, and desktop widths
   — confirm a way to open the export window is present at every size and
   that once open, every option/control remains legible and reachable;
   confirm locale text (English/Spanish) doesn't break either presentation
   at any width (Edge Cases, `spec.md`).

## 3. Automated checks

```sh
cd retro-rocket

# Type-check and lint
npm run type-check
npm run lint

# Unit/component tests + coverage gate (branches 78 / functions 64 / lines 50 / statements 50)
npm run test:coverage

# Architecture boundary — no direct Firestore access from these components
npx vitest run src/test/architecture/retrospective-board-no-firestore.test.ts --config vitest.config.ts

# If any new/changed design tokens were introduced, confirm WCAG contrast math still holds
npx vitest run src/test/lib/theme/contrast.tokens.test.ts --config vitest.config.ts

# E2E: the critical export flow, and accessibility (including the new
# export-window and mobile-viewport coverage)
npm run e2e -- export.spec.ts accessibility.spec.ts
```

**Expected outcome**: all of the above pass with zero regressions and zero
new WCAG 2.1 AA violations (SC-002, SC-003), including new coverage of the
export window's own open/exporting/success/error states and the mobile
bottom-sheet presentation, per `contracts/functional-parity-contract.md`
and `contracts/accessibility-interaction-contract.md`.

  mobile-bottom-sheet presentations, reviewed by the product owner with

  been run against both the baseline and the final implementation.

- A structured design review against Apple HIG principles (clarity,
  deference, depth) closes with zero unresolved high-priority findings
  (SC-005) — recorded in `design-review.md` (analogous to features
  028/029/031/033/036's own design-review documents).
